An **agent** is Egma's stable record of the voice agent under test. A
**connection** is one way the simulator can reach that agent.

Connections are separate records. Each connection has an `agentId` that points
to one agent. An agent API response can include its connections for convenience,
but their identifiers and lifecycles remain separate.

## Five facts describe a connection

| Fact | Meaning | Example |
|---|---|---|
| **Agent platform** | Product or framework that runs the agent | Retell or LiveKit |
| **Connection type** | Path the simulator uses | `retell_text_mode`, `retell_web_call`, `phone_number`, `livekit_room` |
| **Access variant** | How Egma receives access to that path | API key, public number, project credentials, token endpoint |
| **Modality** | Conversation form | `chat` or `voice` |
| **Product label** | Display text derived by Egma | Retell text mode, LiveKit project credentials |

These fields do different jobs. Connection type selects simulator code. Access
variant selects configuration and credential rules inside that adapter.
Modality selects chat or voice behavior. Agent platform records where the
agent runs; it does not select the adapter. Product label is display text and
never selects code.

Current supported combinations include:

| Agent platform | Connection type | Access variant | Modality | Product label |
|---|---|---|---|---|
| Retell | `retell_text_mode` | `retell_text_mode.api_key` | chat | Retell text mode |
| Retell | `retell_web_call` | `retell_web_call.api_key` | voice | Retell web call |
| Retell | `phone_number` | `phone_number.public_e164` | voice | Retell phone |
| LiveKit | `livekit_room` | `livekit_room.project_credentials` | chat | LiveKit chat |
| LiveKit | `livekit_room` | `livekit_room.project_credentials` | voice | LiveKit project credentials |
| LiveKit | `livekit_room` | `livekit_room.customer_token_endpoint` | voice | LiveKit token endpoint |
| LiveKit | `phone_number` | `phone_number.public_e164` | voice | Phone number |
| Any or unknown | `phone_number` | `phone_number.public_e164` | voice | Phone number |

The current connection catalog supplies the LiveKit rows available on one
deployment. The CLI reads it iteratively: the bare LiveKit connect call lists
modalities, `--modality` adds access-variant choices, and `--modality` plus
`--access-variant` adds required field and secret facts. These incomplete calls
write nothing.

## Platform and connection type are independent

A LiveKit worker can answer a public phone number. In that case:

- agent platform is LiveKit;
- connection type is `phone_number`;
- access variant is `phone_number.public_e164`; and
- modality is voice.

The phone adapter does not need to know that LiveKit runs the agent. It dials
the number with Egma's telephony configuration. The same agent can also have a
`livekit_room` connection that joins a room directly.

This model allows future paths, such as WebSocket or WebRTC adapters, without
changing the meaning of agent platform.

## Current connection types

### Retell text mode

`retell_text_mode` conducts a chat simulation with a Retell voice agent. Egma
places no call. The `retell_text_mode.api_key` variant stores the Retell agent
ID and a sealed API key.

Text-mode connections start with mock tools on. Answers ride on the request, so
the lane writes nothing to the Retell account.

### Retell web call

`retell_web_call` is a voice call Egma places over the internet. The
`retell_web_call.api_key` variant stores the Retell agent ID and a sealed API
key.

Web-call connections start with mock tools off. Enabling them is a separate
explicit platform action because a mocked run creates a temporary Retell
version and restores the original state afterward.

### Phone number

`phone_number` is platform-independent and voice-only. Its
`phone_number.public_e164` variant stores a public number such as
`+15551234567`. It stores no provider credential. Egma dials it with the
deployment's telephony route. Phone simulations reach real tools and cannot use
mock tools.

### LiveKit room

`livekit_room` joins a room in the customer's LiveKit project. Project
credentials support chat and voice in the current catalog. A customer token
endpoint supports voice.

- `livekit_room.project_credentials`: Egma stores the project key pair sealed,
  mints a token, creates the room, and dispatches an exact worker name.
- `livekit_room.customer_token_endpoint`: the customer keeps the signing key
  and exposes a public HTTPS endpoint that returns a room token. Egma stores
  only the endpoint authentication headers sealed.

These are access variants of the same connection type, not different agent
platforms.

#### What a LiveKit worker reads

A project-credentials connection can store a `metadata` JSON object inside a
string. Egma gives the same bytes to both LiveKit metadata channels:

| Channel | Worker path | When |
|---|---|---|
| Room metadata | `ctx.room.metadata` | Every simulation |
| Dispatch metadata | `ctx.job.metadata` | Every named-worker dispatch |

Egma adds no scenario, persona, expected behavior, or mock-tool answer to this
metadata. A worker must not receive the test script that defines its simulation.
The room name tells the Egma SDK that the worker is in a simulation.

The customer-token-endpoint variant takes no dispatch name or metadata. Without
the project key pair, Egma cannot create the room or dispatch a named worker;
the customer's endpoint owns those actions.

## Create connections with skills and the CLI

The public `integrate-egma` skill keeps repository discovery read-only and asks
the developer to approve the exact remote plan before `connect` runs.

Retell setup includes provider context for test grounding:

```bash
EGMA_RETELL_API_KEY=... egma connect \
  --platform retell \
  --show-context \
  --retell-agent agent_... \
  --lanes text
```

LiveKit setup first reads modalities, then access variants, then required
fields and secrets. Each incomplete call writes nothing:

```bash
egma connect --platform livekit

egma connect --platform livekit --modality voice

egma connect --platform livekit \
  --modality voice \
  --access-variant livekit_room.project_credentials
```

After the developer approves the exact values, the coding agent supplies the
public fields and secrets in one complete call:

```bash
EGMA_LIVEKIT_API_KEY=... \
EGMA_LIVEKIT_API_SECRET=... \
egma connect \
  --platform livekit \
  --name front-desk \
  --modality voice \
  --access-variant livekit_room.project_credentials \
  --livekit-url wss://acme.livekit.cloud \
  --dispatch-name receptionist
```

The CLI also records the connection receipt in `egma/config.yaml`. Provider
secrets never enter that file.

## Create a connection through the API

Create an agent with an inline Retell text-mode connection:

```json
{
  "name": "order-line",
  "agentPlatform": "retell",
  "connection": {
    "agentPlatform": "retell",
    "connectionType": "retell_text_mode",
    "accessVariant": "retell_text_mode.api_key",
    "modality": "chat",
    "config": { "retellAgentId": "agent_abc123" },
    "credentials": { "apiKey": "key_..." }
  }
}
```

Attach a generic phone connection to an existing agent:

```json
{
  "agentPlatform": null,
  "connectionType": "phone_number",
  "accessVariant": "phone_number.public_e164",
  "modality": "voice",
  "config": { "phoneNumber": "+15551234567" }
}
```

Use `POST /v1/agents/:agentId/connections` for the second request.

<Note>
  A connection is reachable only through its agent. There is no
  `/v1/connections` root. `GET /v1/agents/:agentId` lists one agent's
  connections; `GET /v1/agents` includes connections on every listed agent.
</Note>

Responses include the five connection facts, `id`, topology, environment, safe
configuration, and a credential hint when relevant. Egma never returns stored
secrets.

## One agent can have several connections

Add several connections only when they reach the same logical voice agent:

```text
agent: order-line (agt_01K...)
  connection: Retell text mode (con_01K...)
    platform: Retell
    type: retell_text_mode
    variant: retell_text_mode.api_key
    modality: chat
  connection: Retell phone (con_01K...)
    platform: Retell
    type: phone_number
    variant: phone_number.public_e164
    modality: voice
```

Each run names one `connectionId`. The run freezes that connection's facts so
later edits do not rewrite history.

## Monitoring is separate

A simulation connection tells Egma how to contact an agent during a test.
Monitoring tells Egma how to receive completed production evidence. Monitoring
belongs to the agent, not to a connection.

A Retell agent can name its provider agent, hold a sealed monitoring key, and
carry the **pull production calls** switch. A LiveKit agent needs no polling
switch; its worker pushes spans through the Egma SDK.

Monitoring credentials and simulation connection credentials are separate.
Rotating or disabling one path does not change the other. Turning Retell
monitoring on or off never creates or changes a simulation connection.

The coding agent obtains separate developer approval immediately before
`egma monitoring enable`, then confirms the result with
`egma monitoring status`. A monitoring-only integration stops there. A both
integration completes the approved test run and the monitoring status.

See [Production telemetry](/concepts/telemetry) for the evidence path.
