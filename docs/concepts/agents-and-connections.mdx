An **Agent** is Egma's record of one of your agents. It holds the agent's name, its project membership, and a history of every test run and simulation ever conducted against it. A **Connection** is how Egma reaches that agent when a simulation starts. Its type names the transport or provider. Its modality is either Chat or Voice.

## Agents

Register an agent once and Egma assigns it a stable `agt_` identifier. That identifier ties together everything that runs against that agent: test suites, individual runs, simulation traces, and verdict history. You never need to re-register after an update to your agent's prompt or tooling — the identifier stays the same.

Registering is idempotent by design. If you run `egma connect` a second time for the same vendor agent, Egma looks up the existing registration rather than creating a duplicate. The `registration` field in the response tells you exactly what happened:

| Value | Meaning |
|---|---|
| `created` | A new agent and connection were registered. |
| `reused` | The agent and connection already existed. The stored credentials were updated with what you sent — safe to use for key rotation. No new rows were written. |
| `connection_added` | The agent already existed and a new connection was attached to it. |

This makes it safe to run from CI pipelines or after a network failure — you will never end up with two agent records for one vendor agent.

## Connections

A Connection defines the path from Egma to your agent. One agent can have multiple connections, each representing a different path.

### Connection types

<CardGroup cols={3}>
  <Card title="Retell" icon="phone">
    Exchanges messages with a Retell chat agent. It has the Chat modality and requires a Retell API key and agent ID.
  </Card>
  <Card title="Phone" icon="phone-volume">
    Dials a telephone number through the platform carrier. It has the Voice modality. The connection stores the number, not a Retell credential.
  </Card>
  <Card title="LiveKit" icon="satellite-dish">
    Joins a room in your LiveKit project. It has the Voice modality and uses project credentials or a token endpoint.
  </Card>
</CardGroup>

### Modalities

Each connection has one modality:

<CardGroup cols={2}>
  <Card title="Chat" icon="message">
    Egma exchanges messages with the agent. No audio or telephone call is part of this modality.
  </Card>
  <Card title="Voice" icon="waveform">
    Egma speaks and listens. A Voice connection can use LiveKit or Phone. Phone is a connection type, not a modality.
  </Card>
</CardGroup>

<Tip>
Each run names one connection. Compare runs across connections only when those connections reach the same logical agent.
</Tip>

### Credential sealing

Credentials you provide when creating a connection — API keys, secrets — are **encrypted immediately on arrival** and never stored in plaintext. After creation, they are not readable through any Egma API. The response returns only a `credentials_hint` (the last four characters of the key) so you can confirm a rotation landed without seeing the credential itself.

This is enforced structurally: the sealed field is absent from every read response shape, not merely blanked. There is no serializer path that could accidentally expose it.

## Registering via the CLI

The fastest way to register an agent is with `egma connect`. Run it inside your voice agent repository:

```bash
egma connect
```

The wizard asks for your provider API key (input is masked), lists the agents on your account, and reads the selected Retell agent's modality. A chat agent gets one Retell Chat option. A voice agent gets one Phone option and the wizard asks which routed number to dial.

To run non-interactively (for CI or a coding agent), supply the key and options without a terminal:

```bash
# From an environment variable
EGMA_RETELL_API_KEY=key_... egma connect --reach text

# Piped from a file
cat retell-key.txt | egma connect --reach phone --phone-number +15551234567
```

## Registering via the API

You can also register directly with `POST /api/agents`. Include the connection inline in the same request:

```json
{
  "name": "order-line",
  "connection": {
    "type": "retell",
    "modality": "chat",
    "config": { "retellAgentId": "agent_abc123" },
    "credentials": { "api_key": "key_..." }
  }
}
```

To attach a second connection to an existing agent, use `POST /api/agents/:agentId/connections` with the same connection body.

<Note>
A connection is only ever reachable through its agent. There is no `/api/connections` root. To list the connections on one agent, use `GET /api/agents/:agentId`; to see them for every agent at once, `GET /api/agents` carries them on each listed agent.
</Note>

## One agent, multiple connections

Having multiple connections on one Egma agent keeps its run history unified. Add them only when they reach the same logical agent. The Retell CLI does not invent a second modality for one Retell agent; it creates the path that matches the agent Retell returned.

```
agent: order-line  (agt_01K…)
  └── connection: chat-1   (con_01K…)   type: retell   modality: chat
  └── connection: phone-1  (con_01K…)   type: phone    modality: voice
```

Each run names a specific `connection_id`, so results from each path stay distinct in your history.
