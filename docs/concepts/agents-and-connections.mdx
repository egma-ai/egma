An **agent** is Egma's stable record of the agent you test. A **connection** is
one way Egma can reach that agent for a simulation.

Connections are separate database records. Each connection has an `agentId`
that links it to one agent. An agent does not store a connection inside its own
row. Agent API responses can include related connections as a convenience, but
the two are still separate records with separate identifiers and lifecycles.

## The five simulation facts

Every connection states five separate facts:

| Fact | Meaning | Example |
|---|---|---|
| **Agent platform** | The product or framework the customer uses | Retell, LiveKit Agents, or unknown |
| **Connection type** | The path the simulator uses to reach the agent | `retell_chat_api`, `phone_number`, `livekit_room` |
| **Access variant** | How Egma gets access to that path | API key, public E.164 number, project credentials, token endpoint |
| **Modality** | The conversation form | `chat` or `voice` |
| **Product label** | Display text derived by Egma | Retell chat, Retell phone, LiveKit token endpoint |

These facts do different jobs. The connection type selects simulator code. The
access variant selects the configuration and credential rules inside that
adapter. Modality selects chat or voice behavior. Agent platform records where
the agent runs; it does not select the adapter. Product label is display text
and never selects code.

The supported combinations are:

| Agent platform | Connection type | Access variant | Modality | Product label |
|---|---|---|---|---|
| Retell | `retell_chat_api` | `retell_chat_api.api_key` | chat | Retell chat |
| Retell | `phone_number` | `phone_number.public_e164` | voice | Retell phone |
| LiveKit Agents | `livekit_room` | `livekit_room.project_credentials` | voice | LiveKit project credentials |
| LiveKit Agents | `livekit_room` | `livekit_room.customer_token_endpoint` | voice | LiveKit token endpoint |
| LiveKit Agents | `phone_number` | `phone_number.public_e164` | voice | Phone number |
| Any or unknown | `phone_number` | `phone_number.public_e164` | voice | Phone number |

## Platform and connection type are independent

A LiveKit Agents worker can answer a public phone number. In that case:

- agent platform is LiveKit Agents;
- connection type is `phone_number`;
- access variant is `phone_number.public_e164`;
- modality is voice.

The phone adapter does not need to know that LiveKit Agents runs the agent. It
dials the number with Egma's own telephony configuration.

The same agent can also have a `livekit_room` connection. That connection joins
the customer's LiveKit room directly and does not place a phone call.

This model can add future paths without changing what an agent platform means.
For example, a WebSocket or WebRTC adapter can become a new connection type
with its own access variants and supported modalities.

## Current connection types

### Retell chat API

`retell_chat_api` uses Retell's Chat API. It is chat-only. The
`retell_chat_api.api_key` variant stores a sealed Retell API key and the Retell
chat agent ID.

This connection type does not stand for every way to reach a Retell agent. A
Retell voice agent is reached through a `phone_number` connection today.

### Phone number

`phone_number` is platform-independent and voice-only. Its
`phone_number.public_e164` variant stores a public number such as
`+15551234567`. It stores no provider credential. Egma dials it with the
deployment's telephony configuration.

### LiveKit room

`livekit_room` joins a room in the customer's LiveKit project. It is
voice-only and has two access variants:

- `livekit_room.project_credentials`: Egma stores the project key pair sealed,
  mints a token, creates the room, and can dispatch a named worker.
- `livekit_room.customer_token_endpoint`: the customer keeps the project key
  pair and exposes a public HTTPS endpoint that returns a room token. Egma
  stores only the endpoint authentication headers sealed.

These variants control the same connection type. They are not different agent
platforms.

## Create a connection through the API

Create an agent with an inline Retell chat connection:

```json
{
  "name": "order-line",
  "connection": {
    "agentPlatform": "retell",
    "connectionType": "retell_chat_api",
    "accessVariant": "retell_chat_api.api_key",
    "modality": "chat",
    "config": { "retellAgentId": "agent_abc123" },
    "credentials": { "apiKey": "key_..." }
  }
}
```

Attach a generic phone connection to an existing agent:

```json
{
  "agentPlatform": null,
  "connectionType": "phone_number",
  "accessVariant": "phone_number.public_e164",
  "modality": "voice",
  "config": { "phoneNumber": "+15551234567" }
}
```

Use `POST /v1/agents/:agentId/connections` for this request.

<Note>
A connection is only ever reachable through its agent. There is no `/v1/connections` root. To list the connections on one agent, use `GET /v1/agents/:agentId`; to see them for every agent at once, `GET /v1/agents` carries them on each listed agent.
</Note>

The response includes the five facts, plus `id`, topology,
environment, safe configuration, and a credential hint
when that variant stores a credential. It never returns a stored secret.

## One agent can have several connections

One agent can be tested through several paths while keeping one run history.
Add several connections only when they reach the same logical agent:

```text
agent: order-line (agt_01K...)
  connection: Retell chat (con_01K...)
    platform: Retell
    kind: retell_chat_api
    variant: retell_chat_api.api_key
    modality: chat
  connection: Retell phone (con_01K...)
    platform: Retell
    kind: phone_number
    variant: phone_number.public_e164
    modality: voice
```

Each run names one `connectionId`. The run freezes that connection's facts so
later edits do not rewrite history.

## Monitoring is separate from reaching the agent

A simulation connection tells Egma how to contact an agent during a test.
Monitoring is how Egma receives evidence from real production conversations,
and it belongs to the agent rather than to any connection.

An agent may name the platform that runs it, hold that platform's API key, and
carry one switch: **pull production calls**. With the switch on, Egma polls
Retell for that agent's completed conversations. A LiveKit Agents agent needs no
switch — its own process sends spans over OTLP.

The key an agent holds for monitoring and the credentials a connection holds for
simulations are separate on purpose, so the two jobs never share custody. If you
chat-test and monitor the same Retell account, you enter the key twice, once for
each job. Turning the switch on or off never creates or changes a simulation
connection. See [Production telemetry](/concepts/telemetry).
