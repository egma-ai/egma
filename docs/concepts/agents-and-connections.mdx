An **agent** is Egma's stable record of the voice agent under test. A
**connection** is one way the simulator can reach that agent.

Connections are separate records. Each connection has an `agentId` that points
to one agent. An agent API response can include its connections for convenience,
but their identifiers and lifecycles remain separate.

## Five facts describe a connection

| Fact | Meaning | Example |
|---|---|---|
| **Agent platform** | Product or framework that runs the agent | Retell or LiveKit |
| **Connection type** | Path the simulator uses | `retell_text_mode`, `retell_web_call`, `phone_number`, `livekit_room` |
| **Access variant** | How Egma receives access to that path | API key, public number, project credentials, token endpoint |
| **Modality** | Conversation form | `chat` or `voice` |
| **Product label** | Display text derived by Egma | Retell text mode, LiveKit project credentials |

These fields do different jobs. Connection type selects simulator code. Access
variant selects configuration and credential rules inside that adapter.
Modality selects chat or voice behavior. Agent platform records where the
agent runs; it does not select the adapter. Product label is display text and
never selects code.

Current supported combinations include:

| Agent platform | Connection type | Access variant | Modality | Product label |
|---|---|---|---|---|
| Retell | `retell_text_mode` | `retell_text_mode.api_key` | chat | Retell text mode |
| Retell | `retell_web_call` | `retell_web_call.api_key` | voice | Retell web call |
| Retell | `phone_number` | `phone_number.public_e164` | voice | Retell phone |
| LiveKit | `livekit_room` | `livekit_room.project_credentials` | chat | LiveKit chat |
| LiveKit | `livekit_room` | `livekit_room.project_credentials` | voice | LiveKit project credentials |
| LiveKit | `livekit_room` | `livekit_room.customer_token_endpoint` | voice | LiveKit token endpoint |
| LiveKit | `livekit_room` | `livekit_room.customer_token_endpoint` | chat | LiveKit chat token endpoint |

The current platform catalog supplies these combinations, their required
fields, and their credential fields. Read it with
`egma agent connection options --platform <retell|livekit>`. The command writes
nothing.

## Current connection types

### Retell text mode

`retell_text_mode` conducts a chat simulation with a Retell voice agent. Egma
places no call. The `retell_text_mode.api_key` variant stores the Retell agent
ID and a sealed API key.

A test's mock tools ride on every request Egma sends, so this lane writes
nothing to the Retell account. Its `retell_dynamic_variables` ride with them.

### Retell web call

`retell_web_call` is a voice call Egma places over the internet. The
`retell_web_call.api_key` variant stores the Retell agent ID and a sealed API
key.

Where at least one test of a run names a mock tool, Egma creates one temporary
version of the agent at run start, routes each mocked tool to Egma per call, and
deletes that version when the run ends. Your serving version is never changed.
See [Retell](/integrations/retell#how-a-mocked-web-call-reaches-egma).

### Phone number

The current Retell catalog offers a voice-only public phone Connection. Its
`phone_number.public_e164` variant stores a public number such as
`+15551234567`. It stores no provider credential. Egma dials it with the
deployment's telephony route. Phone simulations reach real tools: this lane
never mocks, and it carries no dynamic variables.

### LiveKit room

`livekit_room` joins a room in the customer's LiveKit project. Both access
variants support chat and voice.

- `livekit_room.project_credentials`: the config names `url` and `agentName`.
  Egma stores the project key pair sealed, mints a token, creates the room, and
  dispatches that exact worker name.
- `livekit_room.customer_token_endpoint`: the config names `tokenEndpoint` and
  `agentName`. The customer keeps the signing key and exposes a public HTTPS
  endpoint in LiveKit's standard token endpoint format. Egma asks it for a room
  token and the server URL, and names the worker to dispatch in the request.
  Egma stores the endpoint URL, the agent name, and the sealed auth headers. It
  stores no server URL. See [LiveKit token endpoint](/integrations/livekit-token-endpoint).

These are access variants of the same connection type, not different agent
platforms. A connection carries no per-call data of its own: what a simulation
starts with is the running test's `env`.

#### What a LiveKit worker reads

Egma writes the running test's `job_dispatch_metadata` to the agent dispatch,
as one compact JSON string, byte for byte. On a key-pair connection Egma makes
that dispatch itself. On a token-endpoint connection Egma sends the same
string to the endpoint inside the request's `room_config`, and the endpoint
copies it into the token it mints:

| Channel | Worker path | What it carries |
|---|---|---|
| Dispatch metadata | `ctx.job.metadata` | The test's `job_dispatch_metadata`, and nothing of Egma's. A test that names none dispatches the empty string |
| Room metadata | `ctx.room.metadata` | Nothing. Egma leaves it empty |

Egma adds no scenario, persona, expected behavior, or mock-tool answer to the
dispatch. A worker must not receive the test script that defines its simulation.
The room name tells the Egma SDK that the worker is in a simulation.

On the customer-token-endpoint variant Egma cannot create the room, so only the
dispatch channel carries anything. Egma names the worker and passes the test's
`job_dispatch_metadata` inside the request's `room_config`. The endpoint copies
that block into the token, and LiveKit dispatches the worker when the room is
created.

## What each connection can use of a test

A test carries its own world: the **mock tools** it answers for itself, and the
**env** the call starts with. Not every connection can carry all of it.

| Connection | Mock tools | `retell_dynamic_variables` | `job_dispatch_metadata` |
|---|---|---|---|
| Retell text mode | Yes | Yes | Not used |
| Retell web call | Yes | Yes | Not used |
| Retell phone | No | No | Not used |
| LiveKit key pair, chat or voice | Yes, with the Egma SDK in your worker | Not used | Yes |
| LiveKit token endpoint | Yes, with the Egma SDK in your worker | Not used | Yes, inside the `room_config` your endpoint copies into the token |

**A run proceeds whatever its connection can carry, and says what it could not
use.** Egma reads the connection and the tests' pinned versions and shows a
short note when a run picks up something this connection cannot carry, such as
mock tools or Retell dynamic variables on a phone run. It appears under the
connection picker when you start the run, and again on the run page. Nothing
is refused for it, and nothing is stored: the note is computed from what the
run holds.

"Not used" means the key belongs to the other platform. One test can carry both
keys and run on either agent; the key the lane does not use is simply not
passed.

## Create Connections with the CLI

The coding agent keeps repository discovery read-only. The developer's
end-to-end request authorizes normal Connection setup after discovery.

Registering an Agent and adding a Connection are separate operations. Retell
example:

```bash
egma agent register --platform retell --name order-line

EGMA_RETELL_API_KEY=... \
  egma agent connection add \
  --agent agt_... \
  --access retell-api-key \
  --modality chat \
  --retell-agent agent_...
```

Read the current LiveKit catalog once, then register an Agent identity:

```bash
egma agent connection options --platform livekit
egma agent register --platform livekit --name front-desk
```

The coding agent supplies the exact public fields and existing secrets in one
Connection command. Project credentials are the normal path:

```bash
EGMA_LIVEKIT_API_KEY=... \
EGMA_LIVEKIT_API_SECRET=... \
egma agent connection add \
  --agent agt_... \
  --access livekit-project-credentials \
  --modality voice \
  --livekit-url wss://acme.livekit.cloud \
  --livekit-agent-name receptionist
```

`agent register` owns only Agent identity. `agent connection add` owns Access,
Modality, provider fields, and setup credentials. The CLI refreshes the Agent
and Connection IDs in `egma/config.yaml`. Provider secrets never enter that
file.

## Create a connection through the API

Create an agent with an inline Retell text-mode connection:

```json
{
  "name": "order-line",
  "agentPlatform": "retell",
  "connection": {
    "agentPlatform": "retell",
    "connectionType": "retell_text_mode",
    "accessVariant": "retell_text_mode.api_key",
    "modality": "chat",
    "config": { "retellAgentId": "agent_abc123" },
    "credentials": { "apiKey": "key_..." }
  }
}
```

Attach a generic phone connection to an existing agent:

```json
{
  "agentPlatform": null,
  "connectionType": "phone_number",
  "accessVariant": "phone_number.public_e164",
  "modality": "voice",
  "config": { "phoneNumber": "+15551234567" }
}
```

Use `POST /v1/agents/:agentId/connections` for the second request.

<Note>
  A connection is reachable only through its agent. There is no
  `/v1/connections` root. `GET /v1/agents/:agentId` lists one agent's
  connections; `GET /v1/agents` includes connections on every listed agent.
</Note>

Responses include the five connection facts, `id`, topology, environment, safe
configuration, and a credential hint when relevant. Egma never returns stored
secrets.

## One agent can have several connections

Add several connections only when they reach the same logical voice agent:

```text
agent: order-line (agt_01K...)
  connection: Retell text mode (con_01K...)
    platform: Retell
    type: retell_text_mode
    variant: retell_text_mode.api_key
    modality: chat
  connection: Retell phone (con_01K...)
    platform: Retell
    type: phone_number
    variant: phone_number.public_e164
    modality: voice
```

Each run names one `connectionId`. The run freezes that connection's facts so
later edits do not rewrite history.

## Monitoring is separate

A simulation connection tells Egma how to contact an agent during a test.
Monitoring tells Egma how to receive completed production evidence. Monitoring
belongs to the agent, not to a connection.

A Retell agent can name its provider agent, hold a sealed monitoring key, and
carry the **pull production calls** switch. A LiveKit agent needs no polling
switch; its worker pushes spans through the Egma SDK.

Monitoring credentials and simulation connection credentials are separate.
Rotating or disabling one path does not change the other. Turning Retell
monitoring on or off never creates or changes a simulation connection.

The monitoring or both prompt already authorizes Agent-scoped setup. For
Retell, the coding agent runs `egma agent monitoring setup` with an explicit
Agent ID and `--platform retell`. For LiveKit, that command prints the public
`integrate-egma` skill handoff and exits incomplete because repository
instrumentation and deployment remain coding-agent work. That public guide is
still being authored; use the Python or JavaScript SDK monitoring guide
directly for now. The CLI does not invent a monitoring health state.

See [Production telemetry](/concepts/telemetry) for the evidence path.
