Egma receives real production conversations through a platform-specific
**Monitoring setup**. Retell uses API polling after a voice conversation
finishes. LiveKit Agents uses OpenTelemetry from the running Python agent
process.

Both paths produce the same Egma conversation record. Egma shows a structured
transcript, tool evidence, supported measures, and production grader work when
the received evidence supports them.

The same grading engine that evaluates simulations can also evaluate production traces. You control the scope on each grader.

## How it works

Open **Monitoring → Set up monitoring** and choose the agent platform.

- **Retell:** enter one platform API key and select the Retell voice agents to
  monitor. Egma imports 30 days of call history and then polls about every 30
  seconds. See [Retell](/integrations/retell).
- **LiveKit Agents:** install the Egma Python SDK and call
  `monitor_livekit(ctx)` before `AgentSession.start`. The worker sends OTLP to
  `POST /v1/traces`.

See [Monitoring setup API](/api/monitoring) for the project setup, health, and
exact Retell retry contracts.

Egma stores the resulting spans and shows each production conversation under
**Monitoring** at `/projects/{projectId}/monitoring/transcripts`. A grader with
`scope: production` or `scope: both` can judge it automatically.

The ingest endpoint also accepts standard OTLP/HTTP in protobuf or JSON form.
This is an advanced path for another instrumented agent process. Environment
variables configure an exporter that the process already creates. They do not
create an exporter or register an OpenTelemetry tracer provider.

## Generic OTLP configuration

If your agent process already creates and registers an OTLP exporter, point it at
Egma with these values:

```bash
OTEL_EXPORTER_OTLP_ENDPOINT=http://your-egma:3100
OTEL_EXPORTER_OTLP_HEADERS=Authorization=Bearer%20egma_your_project_key
```

<Warning>
**Use `%20`, not a space, in the header value.** The `OTEL_EXPORTER_OTLP_HEADERS` environment variable uses URL encoding for the value separator. A literal space causes most SDKs to mis-parse the header and the export will be rejected as unauthenticated.
</Warning>

<Note>
**Either origin works.** The ingest endpoint lives on the API (`3100`), and the web application (`3101`) forwards `/v1/traces` to it. The API is one hop shorter.
</Note>

<Warning>
**Leave `/v1/traces` off the end.** The exporter appends the signal's own path. Give it the base origin.
</Warning>

### LiveKit Agents

Install the Egma Python SDK:

```bash
pip install egma
```

Set the Egma API origin and an existing project API key:

```bash
export EGMA_URL=https://api.egma.ai
export EGMA_API_KEY=egma_sk_...
```

Then call the public helper before `AgentSession.start`:

```python
from egma import monitor_livekit
from livekit import agents


async def entrypoint(ctx: agents.JobContext) -> None:
    monitor_livekit(ctx)
    await ctx.connect()
    # Build the agent and session here.
    await session.start(agent=agent, room=ctx.room)
```

The same helper works for customer-hosted and LiveKit Cloud-hosted Python agents. It preserves a compatible existing provider and LiveKit Cloud observability, sends batches to Egma, and flushes the last batch when the job stops. See [Egma Python SDK](/integrations/python-sdk) for the complete setup and health limits.

## API key requirements

The API key you use for telemetry export must be **project-scoped**. An organization-wide key files spans under no project at all, and those traces will not appear in the dashboard.

To mint a project-scoped key, open **Settings → API keys** in the dashboard and create a key there; every row states its scope. If nothing is appearing under **Monitoring**, first check the platform setup state and then widen the transcript time window.

## Querying traces

Retrieve traces programmatically with `GET /v1/traces`. A time window is always required:

```bash
curl "https://your-egma:3100/v1/traces?from=2024-01-15T00:00:00Z&to=2024-01-16T00:00:00Z" \
  -H "Authorization: Bearer egma_your_project_key"
```

Query parameters:

| Parameter | Required | Description |
|---|---|---|
| `from` | Yes | Start of the window, RFC 3339 to microsecond precision. |
| `to` | Yes | End of the window (exclusive), RFC 3339 to microsecond precision. |
| `project_id` | No | Narrow to a specific project. Leave out to query across your whole organization. |
| `limit` | No | Maximum traces per page. Capped at the API's maximum; zero or non-numeric is refused. |
| `cursor` | No | Paging token from the previous page's `next_cursor`. |

Windows wider than 31 days are refused. There is no default window — every request must name one.

To fetch a single trace, use `GET /v1/traces/:traceId`. The same `from`/`to` window is required:

```bash
curl "https://your-egma:3100/v1/traces/abc123...?from=2024-01-15T00:00:00Z&to=2024-01-16T00:00:00Z" \
  -H "Authorization: Bearer egma_your_project_key"
```

The response includes `turns` (transcript-ordered turn spans), `spans` (top-level non-turn spans), `measures` (computed latency and other metrics), and `verdicts` if any graders have judged the conversation.

## Reading transcripts in the dashboard

Open **Monitoring** in your project's navigation — `/projects/{projectId}/monitoring/transcripts` — to see that project's production conversations, newest first, defaulting to the last 24 hours. Each row shows when the exchange started, how long it ran, how many turns each speaker took, and the first thing the human said. Simulations are not listed here: each one is read under the **Simulation run** that produced it.

Open one to read it as a transcript, at `/projects/{projectId}/monitoring/transcripts/{traceId}`:

- **Alternating `human:` and `agent:` turns** in the order they happened, each with its offset from the start of the conversation and its duration.
- **Expand a turn** to see the timed steps inside it — model inference, speech synthesis, tool calls, turn detection, and speaking.
- **Expand a step** to see exactly what was recorded about it, including any failures.

Failed steps are marked on the turn before you open it, so you can scan for problems without expanding everything.

## Simulation traces and production traces

Egma stores traces from two sources, and the dashboard distinguishes them:

| Source | Filed by | `simulation_id` | Recording |
|---|---|---|---|
| **Simulation** | Egma's own simulator | Present — links to the run | Available if voice modality |
| **Retell production** | Egma's Retell polling process | `null` | No production player in the current UI |
| **LiveKit production** | The LiveKit agent through the Egma SDK | `null` | No production recording is supplied |

Simulation and production evidence use the same trace shape at rest. They do
not all arrive through the same path. The simulator and LiveKit Agents send
OTLP. Retell Monitoring reads provider call history and writes the normalized
conversation through the production writer. The shared store and read path are
the point where these paths meet.

<Note>
`simulation_id` is only returned for traces Egma actually conducted. Your production traces will always show `simulation_id: null`.
</Note>

The current recording player appears only on simulation traces that used a
voice connection. Retell's complete call document can contain a
`recording_url`, and Egma preserves that value in the safe provider payload.
The current trace API and Monitoring UI do not expose a production recording
player. LiveKit production telemetry has not proved a recording contract, so
Egma does not claim one.
