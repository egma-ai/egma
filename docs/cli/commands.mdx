The Egma CLI gives developers and coding agents the same small, promptless
commands. Workflow and repository-specific judgment stay outside the CLI. Each
CLI command performs one named local or remote operation.

Install the `egma-cli` npm package once. It provides the `egma` executable and
requires Node.js 22 or newer.

```bash
npm install --global egma-cli
egma --help
```

## Command tree

```text
egma login
egma logout
egma init
egma pull
egma push

egma agent register
egma agent connection options
egma agent connection add
egma agent monitoring setup
egma agent monitoring stop

egma project api-key create
egma persona list
egma suite create
egma suite delete
egma test delete
egma run create
egma run cancel
egma self-host up
```

Run `--help` at any command group or leaf:

```bash
egma agent --help
egma agent connection --help
egma agent connection add --help
```

The CLI has no wizard, JSON output mode, public validation command, monitoring
status command, or public retry key. It prints readable text and copyable IDs.
Exit `0` means the requested work completed or was already complete. Exit `1`
means it did not complete. Exit `130` means the command was interrupted.

## Repository and authentication rules

Use `--cwd <path>` when the repository or platform workspace is not the current
directory. Only `login`, `logout`, and `init` accept `--url`. Other repository
commands read the platform origin and Project from `egma/config.yaml`.

If `egma/config.yaml` is absent, a repository command stops and tells you to run
`egma init`.

| Environment variable | Purpose |
|---|---|
| `EGMA_HOME` | Changes the machine-local directory that stores saved logins |
| `EGMA_API_KEY` | Uses an existing Egma control-plane key instead of a saved login |
| `EGMA_RETELL_API_KEY` | Supplies a Retell provider key during Connection or monitoring setup |
| `EGMA_LIVEKIT_API_KEY` | Supplies the LiveKit Project key during Connection setup |
| `EGMA_LIVEKIT_API_SECRET` | Supplies the LiveKit Project secret during Connection setup |
| `EGMA_LIVEKIT_TOKEN_ENDPOINT_HEADERS` | Supplies token-endpoint authentication headers as one JSON object |

Provider secrets never belong in command arguments or `egma/config.yaml`.
Credential-backed commands also accept `--credentials-stdin`. It reads exactly
one JSON object with the API credential field names, and it wins over the
environment values.

## `egma login`

Start browser-approved device login for one Egma instance:

```bash
egma login [--url <Egma URL>] [--cwd <path>]
```

Egma prints a short code and approval URL, opens the browser when possible, and
waits for the developer to approve the request. If this machine is already
signed in, run `egma logout` before you sign in again. The CLI asks no terminal
questions.

## `egma logout`

Revoke and remove the saved device login for one Egma instance:

```bash
egma logout [--url <Egma URL>] [--cwd <path>]
```

Logout never revokes `EGMA_API_KEY` from the environment and never changes the
repository's `egma/` folder. It removes the credential file only when it removes
the last saved origin entry. The machine-local Egma directory remains in place.

## `egma init`

Bind the repository to an existing Project and pull its current state:

```bash
egma init [--url <Egma URL>] [--project <Project ID>] [--cwd <path>]
```

`init` never creates a Project and never creates an empty folder before login.
The Project attached to the current credential wins. Otherwise, Egma selects
the only available Project. If several Projects are available, it lists them
and requires `--project`.

Running `init` again for the same Project refreshes the repository like
`egma pull`. If the existing folder points to another Project, move or delete
`egma/` before you initialize again.

The resulting `egma/config.yaml` contains only non-secret repository selectors:

```yaml
format: 4
platform:
  origin: https://app.egma.ai
project:
  id: prj_...
  name: Example Project
agents:
  - id: agt_...
    name: Receptionist
    platform: retell
    connections:
      - id: con_...
        name: Retell text mode
```

Provider Agent IDs, Access, Modality, Connection types, provider configuration,
and credentials stay on the platform.

## `egma pull`

Pull the complete remote repository state:

```bash
egma pull [--cwd <path>]
```

Pull refreshes the Agent and Connection index, suites, and tests. Each Test
contains its own Mock Tools and env. Pull validates the update before it writes
files and keeps local test drafts instead of overwriting them.

## `egma push`

Validate and upload the complete local authoring state:

```bash
egma push [--cwd <path>]
```

If any local file is invalid or a remote version moved, Egma uploads nothing.
Pull, reconcile the files, and push again. The platform API remains the final
authority for every write.

## `egma agent register`

Register only an Egma Agent identity:

```bash
egma agent register \
  --platform <retell|livekit> \
  [--name <Agent name>] \
  [--cwd <path>]
```

This command accepts no Access, Modality, provider identity, Connection
configuration, or provider credential. If `--name` is absent, Egma uses the
repository directory name. The command prints the stable Egma Agent ID and
refreshes `egma/config.yaml`.

## `egma agent connection options`

Read the current server-owned Connection catalog:

```bash
egma agent connection options \
  --platform <retell|livekit> \
  [--agent <Egma Agent ID>] \
  [--credentials-stdin] \
  [--cwd <path>]
```

The platform API owns the valid Access and Modality combinations, required
fields, and credential fields. The command writes nothing.

For Retell, it also lists every provider Agent with its ID and attached phone
numbers once. Initial discovery needs a Retell key:

```bash
EGMA_RETELL_API_KEY=... \
  egma agent connection options --platform retell
```

After the first Retell Connection, pass its Egma Agent ID to reuse the stored
provider credential:

```bash
egma agent connection options \
  --platform retell \
  --agent agt_...
```

The output gives one reusable `agent connection add` shape for each supported
Connection. It does not register an Agent or print registration commands.

## `egma agent connection add`

Add one Connection to an existing Egma Agent:

```bash
egma agent connection add \
  --agent <Egma Agent ID> \
  --access <Access> \
  --modality <voice|chat> \
  [--name <Connection name>] \
  [provider fields] \
  [--credentials-stdin] \
  [--cwd <path>]
```

Access and Modality are always explicit. The Egma Agent supplies the platform,
so this command has no `--platform` flag. `--name` is optional; the platform
product label supplies the default.

The public Access values are:

| Access | Platform | Purpose |
|---|---|---|
| `retell-api-key` | Retell | Chat text mode or voice web call |
| `retell-phone-number` | Retell | Voice call to a routed public number |
| `livekit-project-credentials` | LiveKit | Chat or voice room with a Project key pair |
| `livekit-token-endpoint` | LiveKit | Chat or voice room through a customer token endpoint |

### Retell examples

The first Retell Connection binds the provider Agent identity and seals the
one-time provider key:

```bash
EGMA_RETELL_API_KEY=... \
  egma agent connection add \
  --agent agt_... \
  --access retell-api-key \
  --modality chat \
  --retell-agent agent_...
```

The same Access with `--modality voice` selects a Retell web call. A phone
Connection uses the platform-specific phone flag:

```bash
egma agent connection add \
  --agent agt_... \
  --access retell-phone-number \
  --modality voice \
  --retell-phone-number +14155550111
```

Later Connections reuse the Retell Agent binding and stored credential. A
stored credential wins over a stale environment value, so adding a Connection
does not rotate the key silently.
If the phone Connection is first, include `EGMA_RETELL_API_KEY` and
`--retell-agent` exactly as in the first example.

To supply the first Retell key on standard input, start this command as a child
process and write `{"apiKey":"..."}` directly to its standard input:

```bash
egma agent connection add \
  --agent agt_... \
  --access retell-api-key \
  --modality chat \
  --retell-agent agent_... \
  --credentials-stdin
```

### LiveKit examples

Project credentials:

```bash
EGMA_LIVEKIT_API_KEY=... \
EGMA_LIVEKIT_API_SECRET=... \
  egma agent connection add \
  --agent agt_... \
  --access livekit-project-credentials \
  --modality voice \
  --livekit-url wss://example.livekit.cloud \
  --livekit-agent-name receptionist
```

Customer token endpoint:

```bash
EGMA_LIVEKIT_TOKEN_ENDPOINT_HEADERS='{"Authorization":"Bearer ..."}' \
  egma agent connection add \
  --agent agt_... \
  --access livekit-token-endpoint \
  --modality voice \
  --livekit-agent-name receptionist \
  --livekit-token-endpoint https://example.com/livekit/token
```

Use `--modality chat` for a chat Connection. A token-endpoint Connection takes
no `--livekit-url`; the endpoint returns the LiveKit server URL. See
[LiveKit token endpoint](/integrations/livekit-token-endpoint).

The provider-specific public flags are:

| Option | Meaning |
|---|---|
| `--retell-agent <id>` | Retell Agent ID, required on the first Retell Connection |
| `--retell-phone-number <E.164>` | Retell phone number when required |
| `--livekit-url <wss-url>` | LiveKit Project URL for Project credentials |
| `--livekit-agent-name <name>` | Registered LiveKit Agent name for either LiveKit Access method |
| `--livekit-token-endpoint <url>` | Customer-owned token endpoint |

A Connection carries no per-call data. The data a simulation starts with is
the Test's own `env`: see [Test files](/cli/test-files).

For LiveKit Project credentials, standard input is shaped
`{"apiKey":"...","apiSecret":"..."}`. For a token endpoint, it is shaped
`{"headers":{"Authorization":"Bearer ..."}}`. Use `--credentials-stdin`
with either object.

The CLI refreshes `egma/config.yaml` after a successful remote write. If that
refresh fails, it prints the new remote ID, tells you to run `egma pull`, and
does not repeat the write.

## `egma agent monitoring setup`

Set up production monitoring for one explicit Egma Agent and platform:

```bash
egma agent monitoring setup \
  --agent <Egma Agent ID> \
  --platform <retell|livekit> \
  [--retell-agent <Retell Agent ID>] \
  [--credentials-stdin] \
  [--cwd <path>]
```

For Retell, the command reuses the provider identity and sealed key when they
exist. A monitoring-only path still starts with `agent register`; then setup can
bind `--retell-agent` and accept a one-time key from
`EGMA_RETELL_API_KEY` or `{"apiKey":"..."}` on standard input.

For LiveKit, the CLI cannot edit or deploy the worker. It prints this public
skill installation command and asks the coding agent to use `integrate-egma`:

```bash
npx --yes skills add egma-ai/egma --skill integrate-egma
```

The LiveKit handoff exits `1` because CLI setup did not complete.
The public monitoring guide is still being authored. Follow the
[Python SDK](/integrations/python-sdk) or
[JavaScript SDK](/integrations/javascript-sdk) guide directly for now.

## `egma agent monitoring stop`

Stop monitoring for one explicit Egma Agent and platform:

```bash
egma agent monitoring stop \
  --agent <Egma Agent ID> \
  --platform <retell|livekit> \
  [--cwd <path>]
```

For Retell, this stops future call pulls and keeps existing traces. For LiveKit,
the CLI prints the `integrate-egma` skill handoff and exits incomplete because
the coding agent owns the repository change. The current public skill does not
yet contain the complete monitoring guide.

## `egma project api-key create`

Create a Project-scoped API key:

```bash
egma project api-key create --name <name> [--cwd <path>]
```

The Project comes from `egma/config.yaml`. Egma prints the secret once. The CLI
does not save it or deploy it.

## `egma persona list`

List the personas available to tests in the bound Project:

```bash
egma persona list [--cwd <path>]
```

The output gives readable, copyable persona IDs and names. The command writes
nothing.

## `egma suite create`

Create one remote Suite and its local manifest:

```bash
egma suite create <directory> --name <display name> [--cwd <path>]
```

`<directory>` is one direct child under `egma/tests`, not a Suite ID. If the
remote write completes but the manifest write fails, run `egma pull` before
another create attempt.

## `egma suite delete`

Permanently delete one remote Suite and its Tests:

```bash
egma suite delete <directory> [--cwd <path>]
```

Egma resolves the remote Suite from the local manifest. It deletes remotely
first, then removes only the selected local Suite directory. A remote refusal
leaves every local byte unchanged.

## `egma test delete`

Permanently delete one remote Test:

```bash
egma test delete <suite-directory>/<test-file.md> [--cwd <path>]
```

Egma resolves the remote Test from the Test Version and identity revision stored
in the Markdown file. It asks the platform to delete only if both are still
current. Egma leaves newer content or identity work in place and tells you to
pull. After a successful remote deletion, Egma removes only that local file. An
unpushed draft has no remote identity, so remove that draft directly instead.

## `egma run create`

Push the repository and create one Run:

```bash
egma run create <suite-directory> \
  --agent <Egma Agent ID> \
  --connection <Connection ID> \
  [--name <Run name>] \
  [--cwd <path>]
```

The Suite selector is its local directory, not a Suite ID. The Agent and
Connection selectors are explicit stable IDs. Egma pushes the complete
repository first and creates no Run if the push fails. On success, it prints
the Run ID and a results URL based on the platform origin in
`egma/config.yaml`, then returns. View progress in the web product.

Before a real phone Run, the coding agent must state the Suite, target, and
expected simulation count, warn that calls can cost money, and obtain fresh
developer approval. The CLI does not prompt for that approval.

## `egma run cancel`

Cancel one explicit Run:

```bash
egma run cancel <Run ID> [--cwd <path>]
```

## `egma self-host up`

Start the complete local Egma platform from an Egma source checkout:

```bash
egma self-host up [--cwd <platform-workspace>]
```

The command prepares internal platform credentials, starts the required
services, waits for health, and prints the platform URL. It is the only public
command that uses the Egma platform workspace instead of a voice-agent
repository.
