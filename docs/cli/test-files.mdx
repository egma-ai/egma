The `egma/` directory is a working copy of one Egma project. Commit it to Git.
It contains no secrets.

## Folder structure

One repository can contain several suites. Every direct child of `egma/tests/`
is one suite directory:

```text
egma/
  config.yaml
  tests/
    receptionist-core/
      suite.yaml
      booking.md
      after-hours.md
    northside-ford/
      suite.yaml
      service-appointment.md
```

Do not put tests directly in `egma/tests/`. Do not nest suite directories. The
CLI parses the complete repository before a push, pull, suite create, or run.
One invalid file refuses the operation before a platform write.

## Create a suite before its tests

Create a platform suite and its local manifest with:

```bash
egma suite create receptionist-core --name "Receptionist core"
```

The directory name is only a local path. You may rename it. The suite's stable
ID in `suite.yaml` is its product identity.

You can also create a suite in the browser and run `egma pull`. Egma creates a
portable local directory for the remote suite.

## The suite.yaml manifest

Every suite directory, including an empty suite, has one `suite.yaml` with
exactly two keys:

```yaml
id: ste_01JXMK8P2QN4R6S9T1UV3WX5Y
name: Receptionist core
```

- `id` is the stable suite identity. Do not copy it into another directory.
- `name` is the current display name. Edit it and push to rename the suite.

The manifest has no version, agent, connection, grader, schedule, or run
setting. Pull updates a renamed suite's `name` but does not move its directory.

## Test file format

Each test is one Markdown file inside its suite directory. Format 5 is the only
supported file format:

````markdown
---
format: 5
name: missed-appointment-reschedule
description: The caller missed an appointment and needs another time this week.
version: tstv_01JXMK8P2QN4R6S9T1UV3WX5Y
identity_revision: rev_01JXMK8P2QN4R6S9T1UV3WX5Y
personas:
  - id: prs_01JXMK8P2QN4R6S9T1UV3WX5Y
    name: Impatient caller
---

## Scenario

The caller missed yesterday's appointment and wants to reschedule this week.

## Expected behaviors

1. The agent offers at least two alternative times.
2. The agent confirms the new booking before ending the call.

## Mock tools

### check_availability
```json
{
  "answer": {
    "slots": []
  }
}
```

## Env
```json
{
  "retell_dynamic_variables": {
    "caller_name": "Margaret"
  },
  "job_dispatch_metadata": {
    "tenant": "acme"
  }
}
```
````

| Field | Required | Description |
|---|---|---|
| `format` | Yes | Must be `5` |
| `name` | Yes | The test display name |
| `description` | No | A short explanation |
| `version` | No for a new test | The last synced immutable test-version ID |
| `identity_revision` | No for a new test | The last synced live identity revision |
| `personas` | Yes | Persona IDs and display names. A test says who calls, so it needs at least one |

The body carries the four things a test says, under the four headings above, in
that order. `## Scenario` and `## Expected behaviors` are always written.
`## Mock tools` and `## Env` are written only when the test says something under
them: a test that mocks nothing carries no mock tools heading, and a test that
names no env carries no env heading.

Test files do not contain a suite ID. Their containing suite directory owns
them. A tracked test found under another suite is refused. Tests cannot move
between suites.

Older Markdown formats and `required_capabilities` are not supported. There is
no compatibility reader. A file that claims another format number is refused by
name:

```text
egma/tests/receptionist-core/booking.md uses test file format 4. This Egma
requires format 5 and has no legacy reader.
```

## Scenario and expected behaviors

Write the scenario as a concrete situation, not as a call script. Say who the
caller is, what they want, and any useful context.

Every expected behavior is a sentence that the agent should satisfy. A test
needs at least one expected behavior.

## Mock tools

Add a `## Mock tools` section when this test needs a specific backend state.
Each tool uses a `###` heading and one JSON block holding exactly one of
`answer` and `error`:

````markdown
## Mock tools

### check_availability
```json
{
  "answer": { "slots": [] }
}
```

### book_appointment
```json
{
  "error": "the calendar is unreachable"
}
```
````

The heading is the tool's name, exactly as your agent registers it. The block
says one of `answer` — any JSON value the tool returns — and `error`, the
failure it raises as text. Name each tool at most once.

**Egma mocks exactly the tools this section names. Every other tool the agent
calls runs for real.** A test with no `## Mock tools` section runs against your
real backend from end to end.

A mock tool belongs to the test that writes it, and versions with the test.
There is no project-wide list and no file outside the test.

## Env

Add a `## Env` section when this test needs the agent started in a specific
world. It is one JSON block with at most two keys:

````markdown
## Env
```json
{
  "retell_dynamic_variables": { "caller_name": "Margaret" },
  "job_dispatch_metadata": { "tenant": "acme" }
}
```
````

`retell_dynamic_variables` is what Retell substitutes into the agent's prompt
and tool configuration for the call. Every value is text, and a name beginning
`egma_` is reserved for Egma and refused. `job_dispatch_metadata` is the JSON
object LiveKit hands your worker at `ctx.job.metadata`. The env versions with
the test.

One test may carry both keys. On a run the key for the other platform is simply
not used, and the run says so.

## What validation refuses

`egma push`, `egma pull`, and `egma run create` all parse the complete repository
first. One unreadable file refuses the whole operation before any platform
write, and the message names the file and the reason:

```text
egma/tests/receptionist-core/booking.md: the mock tool "check_availability"
says both answer and error. A mock tool answers with one thing: write whichever
branch the test needs.
```

```text
egma/tests/receptionist-core/booking.md: retell_dynamic_variables names
"egma_caller". A variable beginning egma_ is one Egma says to the simulator
itself; name the variable something the agent's own prompt uses.
```

```text
egma/tests/receptionist-core/booking.md: Env holds "room_metadata"; it holds
retell_dynamic_variables and job_dispatch_metadata, and nothing else.
```

Egma writes every file through one serializer, so `egma pull` straight after
`egma push` changes zero bytes.

## Push the complete repository

```bash
egma push
```

Push validates every suite and test first. It then applies one all-or-nothing
project change. A late conflict writes nothing.

A missing local Suite or Test never means deletion. Push refuses when the
platform has a resource that is absent locally. Pull first, or use the explicit
CLI deletion command:

```bash
egma suite delete receptionist-core
egma test delete receptionist-core/booking.md
```

Egma deletes the remote resource first. It removes the exact local directory or
file only after the platform confirms deletion.

## Pull safely

```bash
egma pull
```

Pull plans the complete update before it changes local files. It preserves
changed versioned tests and unpushed test drafts. If a later local write fails,
Egma restores earlier bytes and removes new paths created by that pull.

A suite name is the unversioned exception. Pull writes its current platform
value.

## Run one exact suite

```bash
egma run create receptionist-core \
  --agent <Egma Agent ID> \
  --connection <Connection ID>
```

The argument is one local Suite directory. The Agent and Connection are
explicit stable IDs from `egma/config.yaml`. Egma pushes the complete
repository before it starts the Run. A failed push creates no Run. On success,
the command prints the Run ID and web results URL, then returns.
