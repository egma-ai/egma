The Egma CLI is a promptless command surface for developers and coding agents.
It is designed so an Agent Skill can contain the workflow while the CLI
performs each named operation. The public `integrate-egma` skill is still being
authored, so use the complete command workflow on this page directly for now.

The CLI does not store a goal or run a setup wizard. The developer puts the goal
and platform in the prompt they give their coding agent.

## Install the CLI

The npm package is `egma-cli`. It installs the `egma` executable and requires
Node.js 22 or newer.

```bash
npm install --global egma-cli
```

The `write-egma-tests` skill is available separately for Test authoring:

```bash
npx --yes skills add egma-ai/egma \
  --skill write-egma-tests
```

Then give your coding agent a clear outcome, for example:

> Set up simulation testing and production monitoring for the Retell agent in
> this repository. Follow the Egma CLI workflow in its documentation.

The goal and platform live in that prompt, not in CLI state. The coding agent
uses the repository and this workflow to decide which command comes next.

## How the work is divided

| Work | Owner |
|---|---|
| State the platform and desired outcome | Developer prompt |
| Inspect the repository and find the exact voice agent | Coding agent |
| Approve browser login | Developer |
| Decide when evidence is unclear or a choice is material | Coding agent, then developer when needed |
| Read or change Egma platform resources | One named CLI command |
| Change voice-agent source or runtime configuration | Coding agent |
| Validate and synchronize the repository | `egma pull`, `egma push`, and `egma run create` |

Every named command asks no terminal questions. Login may wait for browser
approval. Provider credentials come from the environment or one JSON object on
standard input; they never enter CLI arguments or repository files.

## First repository flow

<Steps>
  <Step title="Sign in">
    Run `egma login`. Egma prints a code and approval URL. The developer
    approves the request in a browser.
  </Step>
  <Step title="Initialize the repository">
    Run `egma init`. It selects the Project attached to the login, or the only
    available Project, and pulls its current Agents, Connections, suites, and
    tests. It does not create an empty Project or folder before login.
  </Step>
  <Step title="Inspect the voice agent">
    The coding agent reads committed source and identifies one Retell or LiveKit
    agent. This repository judgment stays with the coding agent, not the CLI.
  </Step>
  <Step title="Register the Egma Agent">
    If `egma/config.yaml` does not already list the target, run
    `egma agent register --platform <retell|livekit>`. This creates only Agent
    identity. It does not add Access, Modality, provider configuration, or
    credentials.
  </Step>
  <Step title="Add simulation access">
    Read current choices with `egma agent connection options`. Supply an
    explicit Retell or LiveKit platform. Then add one Connection with an
    explicit Egma Agent ID, Access, and Modality. `agent connection add` owns
    all provider fields and setup credentials.
  </Step>
  <Step title="Author and synchronize tests">
    List personas with `egma persona list`, create a Suite, and write its
    Markdown Tests. `egma push` validates and uploads the complete repository.
    There is no separate public validation command.
  </Step>
  <Step title="Create a Run">
    Run `egma run create` with a Suite directory, Agent ID, and Connection ID.
    It pushes first, creates no Run if the push fails, and returns the Run ID
    and web results URL. Follow progress in the web product.
  </Step>
  <Step title="Set up monitoring when requested">
    Use `egma agent monitoring setup` with an explicit Agent ID and platform.
    The CLI configures Retell polling. For LiveKit, it prints the future skill
    handoff and exits incomplete because source and deployment work does not
    belong in the CLI. Until that skill guide is complete, follow the Python or
    JavaScript SDK monitoring guide directly.
  </Step>
</Steps>

## Agent and Connection boundaries

An Egma Agent is the stable identity of the voice agent. A Connection is one
way a simulation reaches it.

```text
Egma Agent
└── Connection
    ├── Access
    ├── Modality
    ├── provider fields
    └── optional credential
```

`egma agent register` accepts only Agent Platform and an optional Agent name.
`egma agent connection add` accepts Access, Modality, provider fields, an
optional Connection name, and any one-time credential. The selected Agent
already supplies its platform, so Connection creation has no `--platform`
flag.

The public Access names are self-identifying:

- `retell-api-key`
- `retell-phone-number`
- `livekit-project-credentials`
- `livekit-token-endpoint`

The platform API supplies the supported combinations and required fields. The
CLI does not keep a second catalog.

## The `egma/` folder

`egma init` creates the folder only after it identifies and reads an existing
Project:

```text
egma/
  config.yaml
  tests/
    receptionist-core/
      suite.yaml
      *.md
```

`egma/config.yaml` contains only the platform origin, Project ID and name,
Agent IDs, names and platforms, and Connection IDs and names. Provider IDs,
Access, Modality, Connection type, provider configuration, credentials, and
workflow state stay on the platform.

Each Test is one Markdown file. It carries the complete scenario, personas,
expected behaviors, Mock Tools, and env that the simulation uses. See
[Test files](/cli/test-files) for the format.

## Connection examples

Register a Retell Agent identity, then add a chat Connection:

```bash
egma agent register --platform retell --name Receptionist

EGMA_RETELL_API_KEY=... \
  egma agent connection add \
  --agent agt_... \
  --access retell-api-key \
  --modality chat \
  --retell-agent agent_...
```

Register a LiveKit Agent identity, then add the recommended
Project-credentials voice Connection:

```bash
egma agent register --platform livekit --name Receptionist

EGMA_LIVEKIT_API_KEY=... \
EGMA_LIVEKIT_API_SECRET=... \
  egma agent connection add \
  --agent agt_... \
  --access livekit-project-credentials \
  --modality voice \
  --livekit-url wss://example.livekit.cloud \
  --livekit-agent-name receptionist
```

Credentials are needed only while the platform stores a credential-backed
Connection or configures Retell monitoring. Later Runs use the stored sealed
credential.

## Available commands

| Command | What it does |
|---|---|
| `egma login` | Starts browser-approved device login |
| `egma logout` | Revokes one saved device login and removes its local entry |
| `egma init` | Binds an existing Project and pulls its repository state |
| `egma pull` | Pulls Agents, Connections, suites, and tests |
| `egma push` | Validates and uploads the complete local authoring state |
| `egma agent register` | Registers only an Egma Agent identity |
| `egma agent connection options` | Lists server-owned Connection choices and Retell provider Agents |
| `egma agent connection add` | Adds one Connection to an existing Egma Agent |
| `egma agent monitoring setup` | Sets up Retell monitoring or prints the LiveKit skill handoff |
| `egma agent monitoring stop` | Stops Retell pulls or prints the LiveKit skill handoff |
| `egma project api-key create` | Creates and prints a Project API key once |
| `egma persona list` | Lists the Project's personas |
| `egma suite create` | Creates a remote Suite and local manifest |
| `egma suite delete` | Deletes a remote Suite, then its exact local directory |
| `egma test delete` | Deletes a remote Test, then its exact local Markdown file |
| `egma run create` | Pushes, starts one Run, and prints its web URL |
| `egma run cancel` | Cancels one explicit Run ID |
| `egma self-host up` | Starts a complete local Egma platform |

See [Commands](/cli/commands) for exact flags and credential forms.

## Use a self-hosted instance

Run the platform command from the Egma source checkout:

```bash
egma self-host up
```

Run repository commands from the voice-agent repository. Bind the platform
through login and init:

```bash
egma login --url http://localhost:3101
egma init --url http://localhost:3101
```

Later repository commands read that origin from `egma/config.yaml`.

## Output and exit codes

The CLI prints normal text, headings, lists, and copyable IDs. It has no
`--json` mode and no stable `key: value` output protocol.

- Exit `0`: the requested work completed or was already complete.
- Exit `1`: the requested work did not complete; read the message for the next
  action.
- Exit `130`: the command was interrupted.
