The Egma CLI is a deterministic command surface for coding agents. Public
Agent Skills explain how to discover a voice agent, author grounded tests, and
pause only for a required human action. Named commands perform each local or
remote action.

Every named command asks no terminal questions. It prints one fact per line and
uses its exit code as the next branch. This workflow needs no private agent
driver.

## Requirements

- Node.js 22 or newer
- a coding agent that can use Agent Skills and run shell commands
- a browser where the developer can approve sign-in

The npm package is `egma-cli`. Install it once; it provides the `egma`
executable:

```bash
npm install --global egma-cli
```

## Bootstrap a repository

Install the public skills separately:

```bash
npx --yes skills add egma-ai/egma \
  --skill integrate-egma \
  --skill write-egma-tests
```

Give your coding agent this handoff:

> Use the integrate-egma skill to complete the requested Egma simulation
> testing, production monitoring, or both for this repository's voice agent end
> to end.

The two skills divide the work by purpose:

| Skill | Responsibility |
|---|---|
| `integrate-egma` | First-time repository discovery, Retell or LiveKit setup, human-only pauses, the first suite, a first run, and monitoring |
| `write-egma-tests` | Egma Markdown test authoring, personas, expected behaviors, and test-level mock tools |

## Human and command boundaries

The coding agent performs repository work. Egma performs platform operations.
The developer's end-to-end request authorizes its normal local and remote work.

| Boundary | Owner |
|---|---|
| Inspect committed source and propose one target | Coding agent using `integrate-egma` |
| Approve login request | Developer in the browser |
| State testing, monitoring, or both in the integration request | Developer |
| Resolve the exact resource plan | Coding agent |
| Create or read platform resources | Named Egma command |
| Author and validate local files | Coding agent plus `egma validate` |
| Upload the repository | `egma push` |
| Approve a real phone run and its cost | Developer |
| Start and follow a run | `egma run` |

The coding agent asks only for browser authorization, a missing credential, a
choice it cannot safely infer, an unsafe conflict, or a real phone run that can
cost money.

## Full onboarding flow

<Steps>
  <Step title="Sign in">
    The coding agent runs `egma login`. Egma prints a code and approval URL and
    opens the browser when possible. The developer approves the request there.
  </Step>
  <Step title="Discover one voice agent">
    The coding agent inspects committed source without changing it. It traces
    the platform, prompt, tools, entrypoint, dispatch name, production path, and
    provider identifier boundary.
  </Step>
  <Step title="Read the requested outcome">
    The integration request says testing, monitoring, or both. Monitoring-only skips
    the simulation connection, suite, tests, publish, and run.
  </Step>
  <Step title="Resolve remote setup">
    The coding agent uses repository evidence and live CLI facts to resolve the
    exact platform, voice agent, provider target, connection, and monitoring
    target. It asks only when those facts leave a material choice.
  </Step>
  <Step title="Connect for testing">
    The coding agent runs `egma connect --platform retell --show-context` so the
    test author receives the provider-managed prompt and tools. For LiveKit, it
    reads modalities first, repeats the command with `--modality` to read access
    variants, and repeats it with `--modality` plus `--access-variant` to read
    required fields and secrets. These incomplete calls write nothing. The
    complete command prints `registration_name` before its remote request and
    a registration receipt after Egma confirms the write. If the response is
    unclear or the local record fails, the coding agent runs
    `egma connect record`. It either proves exact receipt IDs or matches the
    settled provider-public identity. Retell recovery uses the provider agent,
    exactly one lane, and a phone number for phone. LiveKit recovery uses the
    server URL and exactly one dispatch name or token endpoint. It also matches
    the settled metadata exactly; omission means the setup had none. The
    attempted `registration_name` is only an optional preference. The command makes no
    remote write and writes the proven or equivalent target to local
    `egma/config.yaml`. `registration-not-found` means no equivalent public
    target exists, not that an exact name is absent. The coding agent uses
    `connection_option` output for ambiguous matches instead of inspecting the
    Egma UI for IDs.
  </Step>
  <Step title="Create the first suite">
    `egma personas` supplies the only valid persona names and IDs. If remote
    suites already exist, the coding agent pulls first. It then creates one
    suite and writes the smallest grounded test set. After an unreachable create
    response or a local manifest failure, it pulls before any new create.
  </Step>
  <Step title="Integrate the LiveKit test path">
    For a Python or JavaScript LiveKit worker, the coding agent adds the matching
    Egma SDK testing entry and writes grounded answers for external-dependency
    tools. Retell does not need this source integration.
  </Step>
  <Step title="Validate and review">
    The coding agent runs focused repository checks and `egma validate`, reads
    every changed file back, and publishes it as part of the end-to-end request.
  </Step>
  <Step title="Run the suite">
    The coding agent names the suite, agent, connection, modality, and expected
    simulation count. A real phone run includes a cost warning and waits for
    approval. `egma run` follows the complete run; its worker flags can own a
    repository-local LiveKit worker for the same command. The command prints an
    idempotency key before the start request. A replay of the exact same unclear
    start uses that key without creating a second run.
  </Step>
  <Step title="Enable monitoring">
    `egma monitoring enable` configures the selected Retell or LiveKit
    production path. For LiveKit, the coding agent installs the latest unpinned
    Egma SDK for the detected language and adds `monitor_livekit(ctx)` in
    Python or `monitorLiveKit(ctx)` in JavaScript. See the
    [Python SDK](/integrations/python-sdk) and
    [JavaScript SDK](/integrations/javascript-sdk). LiveKit enable writes its
    new secret only to a regular `.env` that Git ignores; it never prints that
    secret. The coding agent runs `egma monitoring status` to read the final
    state.
  </Step>
</Steps>

## Available commands

| Command | What it does |
|---|---|
| `egma` | Prints command help |
| `egma login` | Starts browser-approved device login for this machine |
| `egma connect` | Registers a Retell or LiveKit agent and simulation connection |
| `egma connect record` | Proves receipt IDs or matches provider-public identity, then writes the target to local `egma/config.yaml` without a remote write |
| `egma init` | Creates an empty committable `egma/` folder; `--url` can bind it without contacting the platform |
| `egma personas` | Lists machine-readable valid persona IDs and names for the bound project |
| `egma suite create <directory> --name <name>` | Creates a suite and writes its local manifest |
| `egma validate` | Reads and validates the complete folder, including platform persona references |
| `egma pull` | Pulls remote suites, tests, and project mock tools |
| `egma push` | Uploads the complete validated repository as one change |
| `egma run <suite-directory>` | Runs and follows one complete suite |
| `egma monitoring enable` | Enables Retell polling or wires LiveKit push monitoring |
| `egma monitoring status` | Reads the monitoring binding and latest arrival state |
| `egma monitoring disable` | Stops Retell polling while keeping stored evidence and binding |
| `egma monitoring record` | Recovers only a failed local record after remote setup succeeded |
| `egma livekit` | Prints the current LiveKit SDK and worker source contract without signing in |
| `egma self-host up` | Starts a complete local Egma platform |

See [Commands](/cli/commands) for exact flags, environment variables, output,
and exit codes.

## The `egma/` folder

Connection setup or `egma init` creates a committable folder in the voice-agent
repository:

```text
egma/
  config.yaml      format 3 platform, project, agents, and connections
  mock-tools.md    project-wide simulation answers
  tests/
    receptionist-core/
      suite.yaml   stable suite ID and current display name
      *.md         tests in this suite
```

No provider secret belongs in this folder. Tests are ordinary Markdown files,
so the team can review and version them with the voice-agent source. See
[Test files](/cli/test-files) for the format.

## LiveKit catalog and local worker runs

The platform's current connection catalog drives LiveKit setup. Read it through
three iterative, read-only calls. Start with the modality list:

```bash
egma connect --platform livekit
```

Then list the access variants for one modality:

```bash
egma connect --platform livekit --modality voice
```

Then list the required public fields and environment secrets for one access
variant:

```bash
egma connect --platform livekit \
  --modality voice \
  --access-variant livekit_room.project_credentials
```

The three calls print `modality_option`, `access_variant_option`, then
`required_field` and `required_secret` facts in that order. They exit on the
missing input and write nothing. The coding agent uses existing credentials and
the public fields that the chosen catalog entry requests:

- `--name <name>`
- `--modality <chat|voice>`
- `--access-variant <id>`
- `--livekit-url <wss-url>`
- `--dispatch-name <name>`
- `--token-endpoint <https-url>`
- `--metadata <json>`

Connection secrets come only from `EGMA_LIVEKIT_API_KEY`,
`EGMA_LIVEKIT_API_SECRET`, or `EGMA_LIVEKIT_TOKEN_HEADERS`.

A local worker run adds all three flags to one followed run:

```bash
LIVEKIT_URL=wss://acme.livekit.cloud \
LIVEKIT_API_KEY=... \
LIVEKIT_API_SECRET=... \
egma run receptionist-core \
  --worker-entrypoint src/agent.py \
  --worker-dependency-manifest pyproject.toml \
  --worker-dispatch-name receptionist
```

The CLI starts the worker, waits for registration, starts the remote run, and
always stops the worker. It refuses `--no-follow` when it owns the worker.

The developer's end-to-end request authorizes normal worker preparation. The
integration skill adds the latest unpinned Egma Python SDK through the
repository's package manager. The CLI may install or upgrade LiveKit CLI,
create the worker project's `.venv`, and install the declared dependencies with
`uv` or Python `pip`. The coding agent pauses only for an unsafe conflict.

Every run prints `idempotency-key:` before the start `POST`. Use that key only
to replay the exact same start after an unclear response. Ask again first only
for a real phone run. Never reuse it after changing inputs or for a new run.

## Point at a self-hosted instance

Run platform commands from the Egma platform workspace:

```bash
egma self-host up
```

Run repository commands from the separate voice-agent repository. Pass the URL
to login and the first setup command, or bind it once with `init`:

```bash
egma login --url http://localhost:3101
egma init --url http://localhost:3101
```

`init --url` only writes the normalized platform origin. It does not contact
the instance. Later commands resolve the URL from `egma/config.yaml`.

## Use in automation

Named commands already have plain output and no terminal questions. Supply all
required choices as flags or environment variables, branch on the exit code,
and read the `status:` line. Login still needs a developer to approve the
device request in a browser. The developer's end-to-end request authorizes normal
repository and remote writes; a real phone run still needs immediate approval.
