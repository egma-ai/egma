The Egma CLI is the official command-line interface for Egma. It connects your voice agent to the platform, generates a first suite of tests grounded in your actual code and prompts, and starts simulations — all in a single command. You can drive it interactively with the built-in wizard, or run every step as a plain scriptable command for CI and coding-agent workflows.

## Requirements

You need **Node 22 or newer**. You do not need to install the package globally — `npx` handles it on demand. Install at least one supported coding agent: Claude Code, Codex, Cursor, or OpenCode.

## Running the CLI

Run the CLI from the root of your voice-agent repository:

```bash
npx @egma/cli
```

No global install is needed. The command the package registers is `egma`, so if you do install it globally you call it the same way.

<Note>
  Run `npx @egma/cli` from the directory that holds your agent's code and
  prompts. If Egma cannot find a voice agent there, run it again from the right
  folder or configure the voice agent in the Egma UI.
</Note>

<Note>
  The wizard onboards new repositories. A repository that already has an `egma/`
  folder gets a polite refusal instead of a second setup — delete or rename the
  folder to redo it, or use `egma push` and `egma run` on what is already there.
</Note>

## The interactive wizard

Running `npx @egma/cli` with no arguments opens the full interactive wizard. It walks you through every step in order and asks one question at a time. On the welcome screen, `[Enter]` starts CLI authorization. After authorization, you choose a coding agent and a later `[Enter]` starts the repository work.

<Steps>
  <Step title="Sign in">
    Egma shows a short device code and opens your browser to a page that already has it pre-filled. Approve it there (creating an account first if you are new). No secret is ever typed into the terminal — the key Egma receives is written to `~/.egma/credentials`, readable only by you.
  </Step>
  <Step title="Choose your coding agent">
    Only after authorization succeeds, Egma finds installed Claude Code, Codex, Cursor, and OpenCode commands. If it finds more than one, you choose which one to use. The same process and successful ACP session keep the context for discovery and test writing.
  </Step>
  <Step title="Discover your agent">
    Egma starts the coding agent you already have and hands it internal notes on voice-agent architecture. Your coding agent reads your repository and reports: which framework runs the agent, where its prompts live, where its tools are defined, how it reaches production, and where its identifier is stored. Every action appears on screen as it happens. Your code and prompts never leave your machine.
  </Step>
  <Step title="Say what Egma is for">
    Once Egma knows your agent and the platform that runs it, it asks one question: should Egma **test** the agent, **watch its production traffic**, or **both**. Testing is the lane below. Monitoring sets up production capture and ends there — no connection, no suite, no tests. Both sets monitoring up first, says so, and then runs the whole testing lane in the same sitting: every shared question is asked once, one agent row serves both jobs, and the last screen points at the graded run and at Monitoring.
  </Step>
  <Step title="Watch production traffic (monitoring and both)">
    On **Retell**, Egma opens your account with one pasted key, shows its voice agents with what Egma already knows about each — registered here, already watched — and starts watching the one you pick, registering it if it is new. It waits briefly for the first imported conversation, and an account with nothing to import ends just as well with a sentence that says so.

    On **LiveKit**, your own coding agent adds the monitoring call for your
    worker language: `monitor_livekit(ctx)` in Python or `monitorLiveKit(ctx)`
    in JavaScript. The JavaScript path needs `@egma/livekit` to be available on
    npm. You watch the edit happen. Egma then mints a project API key, writes
    the two environment lines the SDK reads into `.env` without a separate
    approval screen when Git already ignores that file, and prints them for
    wherever the worker really runs. Nothing waits: a LiveKit worker pushes its
    own evidence, so conversations appear once real traffic starts.

    A start Egma cannot make is explained in plain words — what happened and what to do — and the walk exits with a nonzero code.
  </Step>
  <Step title="Connect your agent">
    For Retell, Egma asks for your API key, lists the voice agents it can read, and asks how it should test the one you choose: in text, over a web call it places, or down one of the agent's public phone numbers. Several lanes can be picked at once and land on one Egma agent. For LiveKit, project credentials are the recommended room setup; a public HTTPS token endpoint with auth headers is the advanced option. Egma uses credentials for discovery and sends them to the platform only when the selected connection needs sealed storage. Pipecat and Vapi setup are not supported yet.
  </Step>
  <Step title="Generate a test suite">
    The wizard creates a real suite on Egma before it writes exactly four tests. It stores
    the stable suite ID in `egma/tests/<suite-directory>/suite.yaml`. The same
    coding-agent session then writes the tests inside that suite directory. The
    screen shows the coding agent's live messages, commands, and file actions while
    it works.
  </Step>
  <Step title="Write the mocked world (LiveKit)">
    On a Python LiveKit worker, the same coding-agent session adds the Egma
    SDK's testing entry and writes `egma/mock-tools.md`: one grounded answer
    per real tool, read out of your own tool code, plus the failure-branch
    answers inside the tests that need one. Before the run, Egma starts the
    discovered worker locally with LiveKit CLI 2.18.2 or newer, waits for it
    to register, and stops it when the run ends. It does not deploy the
    worker. The JavaScript SDK is monitoring-only today, so the wizard stops
    before simulation setup for an Agents JS worker. On Retell nothing is
    written — mock tools are not served there yet.
  </Step>
  <Step title="Review and run">
    The wizard shows the full list of generated tests and the mocked world they will run in. Press `[q]` to quit with every file saved to your repository for later, or `[Enter]` to push the suite and start a run immediately.
  </Step>
  <Step title="Run and grade the complete suite">
    The wizard follows every simulation until execution ends and every completed trace has terminal grading. The results address is a clickable terminal link; press `[Enter]` to open it in your browser. The same plain address remains in your terminal after the wizard closes.
  </Step>
</Steps>

<Tip>
  Over SSH or in a container without a browser? Press `[c]` during sign-in and
  Egma copies the approval URL to your local clipboard. Approve it in a browser
  on your local machine, then paste the URL or the code back into the terminal.
</Tip>

## Available commands

Every step the wizard takes is also available as a standalone command that prints one fact per line and exits with a number you can branch on — perfect for CI pipelines and coding agents.

| Command | What it does |
|---|---|
| `egma` | Opens the interactive wizard |
| `egma login` | Signs this machine in, no questions asked |
| `egma connect` | Registers your voice agent and a reach method |
| `egma init` | Creates the `egma/` folder in your repository |
| `egma suite create <directory> --name <name>` | Creates a suite on Egma and writes its local manifest |
| `egma pull` | Writes Egma's current test versions into your local files |
| `egma push` | Uploads your local tests to Egma |
| `egma run <suite-directory>` | Runs one complete local suite against your connected agent |
| `egma monitoring enable` | Starts watching this agent's production traffic |
| `egma monitoring disable` | Turns the switch off, keeping everything stored |
| `egma monitoring status` | Prints the switch, the binding, the key hint, and the last arrival |
| `egma monitoring record --agent <id>` | Recovers only the repository record after remote setup succeeded; LiveKit also requires the receipt's `--monitoring-key-id` |
| `egma self-host up` | Starts a full local Egma instance |

See [Commands](/cli/commands) for full reference documentation on flags, exit codes, and environment variables.

## The `egma/` folder

The wizard (or `egma init`) creates an `egma/` folder in your repository. Everything in it is committed to version control — nothing secret ever lands there, so there are no `.gitignore` lines to write.

```
egma/
  config.yaml      names and IDs pointing at your Egma instance
  mock-tools.md    mocked tool responses for simulations
  tests/
    receptionist-core/
      suite.yaml   stable suite ID and current display name
      *.md         tests in this suite
    northside-ford/
      suite.yaml
      *.md
```

Your tests are code. Your team reviews them in pull requests, edits them in the same editor, and keeps their history in the same git log. See [Test Files](/cli/test-files) for a full explanation of the file format.

## How the CLI works with coding agents

The CLI communicates with your coding agent over the [Agent Client Protocol](https://agentclientprotocol.com). It checks this machine for Claude Code, Codex, Cursor, and OpenCode. It then starts only the agent you choose. Discovery and test writing use one coding-agent process and one successful ACP session, so they share context.

Egma answers every permission request the agent raises and starts it in the most permissive mode available, so you are not interrupted mid-flow. Every action the agent takes is shown on screen as it happens.

<Warning>
  Any file whose name starts with `.env` is always refused when the agent
  requests it through Egma. Secrets must not enter a model's context. Egma
  refuses the file, tells the agent to work from your code instead, and asks
  you for anything it still needs.

  This holds while Egma sets monitoring up on LiveKit, where a `.env` really is
  written: the two environment lines are written by Egma's own code without a
  separate approval screen, and only when Git already ignores the file. Your
  coding agent still never opens it.
</Warning>

## Installing Egma's skills into your coding agent

At the end of the wizard, Egma asks whether you want to install its public skills into the selected coding agent, so it can drive Egma on its own:

- **`[p]` Project** — writes them into this repository. Commit them and your whole team has them.
- **`[g]` Global** — writes them beside the coding agent, active for every repository you open.
- **`[s]` Skip** — writes nothing. `egma --help` is enough for any coding agent to drive the full product.

The offer carries every skill this release ships — `egma`, `integrate-egma`, and `write-egma-tests`.

The files are written by the [`skills`](https://skills.sh) installer, which ships inside the Egma package at a pinned version. Nothing is downloaded when you accept, and Egma repeats the installer's own lines saying where each skill landed.
At project scope, the real files live in `.agents/skills/`. For Claude Code,
`.claude/skills/<skill>` is a symlink to that canonical copy.

## Pointing at your own Egma instance

If you run Egma self-hosted, pass `--url` to name your instance:

```bash
npx @egma/cli --url http://localhost:3101
```

To avoid repeating the URL, run `egma init --url http://localhost:3101` once. That command normalizes the URL and writes it into `egma/config.yaml` without contacting the platform. Every subsequent command in that repository finds it there automatically.

## Running headlessly in CI

Pass `--headless` to skip the interactive terminal and receive plain lines instead. Combined with the right environment variables, the full sign-in and connect flow runs without any human in the loop:

```bash
EGMA_RETELL_API_KEY=your_key EGMA_LANES=text npx @egma/cli --headless
```
