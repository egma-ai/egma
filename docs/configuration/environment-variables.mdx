Copy `.env.example` to `.env` before you start the platform. Most variables have working defaults that are safe to leave alone. Twelve do not — the deployment refuses to start if any one of them is absent, printing the name of the missing variable rather than guessing at a value. Those twelve are your deployment's own secrets and its own address: a default for any of them would be a value every reader of this repository already holds.

The sections below separate what you must supply from what you can safely leave at its default.

---

## Required variables

Set all nine of the following before running `egma self-host up`. The remaining three (`EGMA_BASE_URL`, `EGMA_LIVEKIT_API_KEY`, `EGMA_LIVEKIT_API_SECRET`) are set automatically by `egma self-host up` and do not need to be set by hand unless you are driving `docker compose` directly.

<ParamField path="EGMA_ENCRYPTION_KEY" type="string" required>
  32 random bytes encoded as 64 hex characters. Seals connection credentials and the carrier SIP password stored in Postgres. Back this up alongside the database — the sealed values are unrecoverable without it.

  ```bash
  openssl rand -hex 32
  ```
</ParamField>

<ParamField path="EGMA_AUTH_SECRET" type="string" required>
  A random base64 string that signs session cookies. The API refuses to start without one.

  ```bash
  openssl rand -base64 32
  ```
</ParamField>

<ParamField path="EGMA_SIMULATOR_SERVICE_TOKEN" type="string" required>
  The bearer token the simulator presents when claiming simulation work from the API. The API checks it on every claim request — the responses carry live provider credentials. Must start with the prefix `egma_st_` so leak-scanning tools can recognise it.

  ```bash
  echo "egma_st_$(openssl rand -hex 32)"
  ```
</ParamField>

<ParamField path="EGMA_S3_ACCESS_KEY_ID" type="string" required>
  The MinIO root credential username. You choose this value — minimum 8 characters. This credential has full write, delete, and list access to the object store, so treat it as a secret and **change `EGMA_S3_SECRET_ACCESS_KEY` before opening the store port to a network**.
</ParamField>

<ParamField path="EGMA_S3_SECRET_ACCESS_KEY" type="string" required>
  The MinIO root credential password. You choose this value — minimum 8 characters. Paired with `EGMA_S3_ACCESS_KEY_ID` above.
</ParamField>

<ParamField path="EGMA_S3_INGEST_ACCESS_KEY_ID" type="string" required>
  The username of the credential Egma writes production evidence with. You choose this value — minimum 8 characters. The deployment creates a MinIO user from it on first start, confined to the `pending/` prefix of the ingestion bucket, so it can never read, delete, or expire a recording.

  Required for every deployment that accepts evidence, which is every deployment that is not a read-only replica. There is no default for the same reason the root pair has none.

  ```bash
  echo "EGMA_S3_INGEST_ACCESS_KEY_ID=$(openssl rand -hex 8)"
  ```
</ParamField>

<ParamField path="EGMA_S3_INGEST_SECRET_ACCESS_KEY" type="string" required>
  The password paired with `EGMA_S3_INGEST_ACCESS_KEY_ID`. You choose this value — minimum 8 characters.

  ```bash
  echo "EGMA_S3_INGEST_SECRET_ACCESS_KEY=$(openssl rand -base64 24)"
  ```
</ParamField>

<Note>
  **The read credentials below are created by the deployment on first start.** The deployment's `minio-init` job creates a restricted user that can fetch one object at a time and cannot write, delete, or list. Copy both values from your startup logs the first time you run `egma self-host up`, then paste them here and restart.
</Note>

<ParamField path="EGMA_S3_READ_ACCESS_KEY_ID" type="string" required>
  The MinIO read-only credential username. Created by the deployment on first start — copy from startup logs.
</ParamField>

<ParamField path="EGMA_S3_READ_SECRET_ACCESS_KEY" type="string" required>
  The MinIO read-only credential password. Created by the deployment on first start — copy from startup logs.
</ParamField>

### Variables set automatically by `egma self-host up`

If you drive `docker compose` directly without the CLI, supply these three yourself. If you use `egma self-host up`, the CLI generates and writes them for you and they do not need to appear in `.env`.

<ParamField path="EGMA_BASE_URL" type="string" required>
  The full public URL of your instance — scheme, host, and port only. No path, query string, or trailing slash. Example: `http://localhost:3101`.

  Egma uses this origin for browser-facing links and trusted browser requests. If others reach your instance at `http://192.168.1.10:3101`, this must say exactly that — not `http://localhost:3101`.
</ParamField>

<ParamField path="EGMA_LIVEKIT_API_KEY" type="string" required>
  The API key used to authenticate the LiveKit media server, simulator, and SIP gateway with each other. Generated by `egma self-host up` and written to `.egma-platform/platform.env`. Do not choose this value manually.
</ParamField>

<ParamField path="EGMA_LIVEKIT_API_SECRET" type="string" required>
  The API secret paired with `EGMA_LIVEKIT_API_KEY`. Generated alongside it by `egma self-host up`.
</ParamField>

## Optional variables with defaults

All variables in this section have working defaults. Override them only when the default conflicts with your environment — for example, if the default ports are already in use on the host.

### PostgreSQL

<ParamField path="POSTGRES_USER" type="string" default="Egma">
  The PostgreSQL role name used by the API.
</ParamField>

<ParamField path="POSTGRES_PASSWORD" type="string" default="Egma">
  Password for `POSTGRES_USER`. Change this — and narrow or close the bind address — before exposing port 5433 to any network.
</ParamField>

<ParamField path="POSTGRES_DB" type="string" default="Egma">
  The PostgreSQL database name.
</ParamField>

<ParamField path="POSTGRES_PORT" type="number" default="5433">
  The port PostgreSQL publishes on the host. Published as 5433 (not 5432) to avoid colliding with a PostgreSQL instance already running on the machine.
</ParamField>

<ParamField path="POSTGRES_BIND" type="string" default="127.0.0.1">
  The address PostgreSQL binds to on the host. Loopback by default — this is a security decision, not an omission. The password above is printed in this repository; binding to `0.0.0.0` on a shared network hands every row in the database to whoever can route to the machine. Widen it only when something off this machine must reach the database, and change `POSTGRES_PASSWORD` at the same time.
</ParamField>

### ClickHouse

<ParamField path="CLICKHOUSE_USER" type="string" default="Egma">
  The ClickHouse user name. Holds every conversation trace your platform records.
</ParamField>

<ParamField path="CLICKHOUSE_PASSWORD" type="string" default="Egma">
  Password for `CLICKHOUSE_USER`. Same caution as `POSTGRES_PASSWORD` applies.
</ParamField>

<ParamField path="CLICKHOUSE_DB" type="string" default="Egma">
  The ClickHouse database name.
</ParamField>

<ParamField path="CLICKHOUSE_PORT" type="number" default="8124">
  The port ClickHouse publishes on the host. Published as 8124 (not 8123) to avoid collisions.
</ParamField>

<ParamField path="CLICKHOUSE_BIND" type="string" default="127.0.0.1">
  The address ClickHouse binds to on the host. Loopback by default for the same reason as `POSTGRES_BIND`.
</ParamField>

### Object storage (S3 / MinIO)

<ParamField path="EGMA_S3_BUCKET" type="string" default="egma-recordings">
  The bucket recordings land in. Created on first start. Change this only if you are pointing Egma at a bucket you already own.
</ParamField>

<ParamField path="EGMA_S3_REGION" type="string" default="">
  The AWS region included in object-store request signatures. Leave empty for MinIO, which ignores regions entirely. Set to the real region (for example, `us-east-1`) when pointing Egma at Amazon S3 — the API refuses to start on an `amazonaws.com` endpoint without one rather than silently signing everything for the wrong region.

  Both the simulator (upload) and the API (playback-link signing) read this value, so set it once here and both halves use the same region.
</ParamField>

<ParamField path="EGMA_S3_PORT" type="number" default="9000">
  The port MinIO publishes on the host. Change this when port 9000 is already taken, and update `EGMA_BLOB_PUBLIC_URL` to match.
</ParamField>

<ParamField path="EGMA_S3_BIND" type="string" default="127.0.0.1">
  The address MinIO binds to on the host. Loopback by default — what answers on this port is the store's admin surface. Set to `0.0.0.0` only when browsers that play recordings are not on this machine, and update `EGMA_BLOB_PUBLIC_URL` to the address those browsers use.
</ParamField>

<ParamField path="EGMA_BLOB_PUBLIC_URL" type="string" default="http://localhost:9000">
  The address **a browser** uses to reach the object store. This is not the address the API uses internally — confusing the two is the most common cause of `SignatureDoesNotMatch` errors on recording playback.

  Set this to the same host as `EGMA_BASE_URL`, on port 9000 (or whatever `EGMA_S3_PORT` is). If `EGMA_BASE_URL` uses `https:`, this must also use `https:` — browsers block mixed-content audio before the request is sent.
</ParamField>

### Ingestion

Production evidence is accepted into a second bucket on the same MinIO, and Egma answers a request successfully only once the evidence is durable there. Everything in this section has a working default; the credential that reaches the bucket is in the required section above.

<Note>
  **The bundled MinIO runs on one node, so its durability is your host's.** The volume survives a container being replaced. It does not survive the loss of that host or its disk. Point `EGMA_INGEST_ENDPOINT` at a store that is remote from this machine — Amazon S3, or any S3-compatible service with a durability promise of its own — if your production evidence must survive either.
</Note>

<ParamField path="EGMA_INGEST_BUCKET" type="string" default="egma-ingestion">
  The bucket accepted evidence waits in. Created on first start beside the recordings bucket. It is a spool rather than an archive: Egma writes the evidence to ClickHouse soon afterwards and deletes the object.
</ParamField>

<ParamField path="EGMA_INGEST_ENDPOINT" type="string" default="http://minio:9000">
  The address **Egma itself** reaches the ingestion bucket at, from inside the deployment's own network. This is the one place in this file where that address and a browser's are genuinely different settings pointing at one MinIO: a recording is fetched by a browser from `EGMA_BLOB_PUBLIC_URL`, and a segment is uploaded by Egma from here.

  Scheme, host, and port only. A path, a query string, or a credential in this URL is refused rather than half-honoured.
</ParamField>

<ParamField path="EGMA_INGEST_REGION" type="string" default="">
  The AWS region included in ingestion request signatures. Defaults from `EGMA_S3_REGION`. Leave empty for MinIO. Set to the real region when pointing this at Amazon S3 — the API refuses to start on an `amazonaws.com` endpoint without one.
</ParamField>

<ParamField path="EGMA_INGEST_ACCESS_KEY_ID" type="string">
  The credential the API signs ingestion requests with. Defaults from `EGMA_S3_INGEST_ACCESS_KEY_ID`, so a deployment using the bundled MinIO sets only that one. Set this directly when the ingestion bucket lives somewhere other than the bundled store.
</ParamField>

<ParamField path="EGMA_INGEST_SECRET_ACCESS_KEY" type="string">
  Paired with `EGMA_INGEST_ACCESS_KEY_ID`. Defaults from `EGMA_S3_INGEST_SECRET_ACCESS_KEY`.
</ParamField>

<ParamField path="EGMA_ROLE" type="string" default="all">
  Which halves of ingestion this process serves: `all`, `ingest`, or `drain`.

  `all` is what this deployment runs — one process accepts evidence and drains the spool. The other two exist so that splitting those apart on a larger deployment later is this one setting rather than a second image and a second protocol. Exactly one process drains per deployment, whichever roles are running.
</ParamField>

<ParamField path="EGMA_INGESTION_LOG_DIR" type="string" default="/var/lib/egma/ingestion">
  Where accepted evidence waits between being staged and being durable. A directory on the `api-ingestion` named volume, holding evidence Egma has taken responsibility for and has not made durable yet. A restart reads it back.

  `docker compose down -v` deletes this volume. Doing that with a backlog in it throws away evidence Egma has already answered success to.
</ParamField>

<ParamField path="EGMA_INGESTION_LOG_MAX_BYTES" type="number" default="536870912">
  How many bytes that staging area holds before Egma starts refusing new evidence. Past it the door answers a retryable failure and nothing already staged is discarded to make room.

  512 MiB is a documented starting value chosen to sit inside an ordinary root disk, not a proven capacity. On the bundled deployment this volume shares the disk with everything else.
</ParamField>

<ParamField path="EGMA_INGESTION_LOG_MAX_RECORDS" type="number" default="200000">
  How many staged records it holds before the same refusal. Both bounds bind, because records are not all one size: a bound in bytes alone is reached after ten conversations on one deployment and ten million on another.
</ParamField>

<ParamField path="EGMA_INGESTION_FLUSH_MILLISECONDS" type="number" default="500">
  How long the oldest staged record waits for company before its segment is sealed and uploaded. A low-volume deployment lives on this number: one conversation's spans must not wait for a batch that will never fill. Raising it trades visibility for fewer, larger objects.
</ParamField>

<ParamField path="EGMA_INGESTION_SEGMENT_MAX_BYTES" type="number" default="8388608">
  How large one segment gets before it seals regardless of the clock. Counts uncompressed evidence, and sits under the trace store's own insert bound so one segment is at most one or two inserts.
</ParamField>

<ParamField path="EGMA_INGESTION_SEGMENT_MAX_RECORDS" type="number" default="5000">
  The same bound in records.
</ParamField>

<ParamField path="EGMA_INGESTION_REQUEST_TIMEOUT_MILLISECONDS" type="number" default="10000">
  How long a request waits for the object store before Egma answers it retryably. Past this the sender is told to try again and the staged evidence stays eligible for upload, so a slow store costs a retry rather than a false success. It is never unbounded.
</ParamField>

<ParamField path="EGMA_INGESTION_SCAN_INTERVAL_MILLISECONDS" type="number" default="30000">
  How often the whole pending spool is listed. That listing is the recovery authority and runs once at startup as well — handing a freshly uploaded segment straight on is a speed hint, and a hint that is lost or delivered twice must not be able to lose evidence.
</ParamField>

### What the ingestion defaults measure as

Numbers, not adjectives, from one bounded measurement of exactly these defaults on one machine: a 4-vCPU, 16 GiB VM running the API, PostgreSQL, ClickHouse, a loopback MinIO, and the load generator all at once, with records of about 2,750 evidence bytes. A dedicated host does better; an object store across a real network moves the acknowledgement tail. Nothing below is extrapolated.

| Measured | Value |
| --- | --- |
| Sustained acceptance at 128 concurrent senders | ~170 conversations/s — 4,600 spans/s, 4.65 MB/s of evidence — held across three 60–75 s runs with every request answered 200 |
| Acknowledgement latency at that rate | p50 0.85 s, p95 1.15–1.18 s |
| Acknowledgement floor when nearly idle | ~0.5 s — a lone conversation's wait is the flush interval |
| Readable after acknowledgement | p50 under 90 ms, p95 under 120 ms, through the standing drainer alone; none of 1,180 measured conversations failed to become readable |
| Compression on the wire to the store | gzip ≈ 8.3:1 on full segments |
| Refusal onset | exactly at the configured bounds — the byte bound refuses with less than one frame of headroom left, the record bound on the record after the last — always retryably, never discarding anything staged |

Past 128 concurrent senders this machine buys almost no additional throughput and pays double the latency: one API process saturates one core. And the byte bound read as an outage buffer, by arithmetic on the measured peak: 512 MiB of staging holds roughly 110 seconds of peak-rate evidence, which is the window an object-store outage has before the door stops staging new evidence and starts refusing it.

### API and web ports

<ParamField path="EGMA_API_PORT" type="number" default="3100">
  The port the API publishes on the host.
</ParamField>

<ParamField path="EGMA_WEB_PORT" type="number" default="3101">
  The port the web application publishes on the host. This is the port that appears in `EGMA_BASE_URL` for a default deployment.
</ParamField>

### Access and security

<ParamField path="EGMA_SINGLE_ORGANIZATION" type="boolean" default="true">
  When `true`, the first person to sign up claims the instance and becomes its admin. Open signup closes behind them — everyone after arrives by invitation. Set to `false` only for a multi-tenant deployment that intentionally holds many separate organizations.
</ParamField>

<ParamField path="EGMA_TRUST_PROXY" type="boolean" default="false">
  Whether to trust `x-forwarded-proto` and `x-forwarded-host` headers. Set to `true` only when a reverse proxy you control (nginx, Caddy, a load balancer) sits in front of the API — otherwise any client can claim any origin.
</ParamField>

<ParamField path="EGMA_RATE_LIMIT_PER_MINUTE" type="number" default="600">
  The maximum number of authenticated requests one organization may make per minute. The budget belongs to the organization, not to a key, so rotating a key does not reset it.
</ParamField>

### Email (optional)

Email is entirely optional. Without it, invitation links are returned directly to the admin who created them, signup requires no verification, and password-reset links are written to the platform log.

<Warning>
  Before adding a second person to an instance that has no mail transport configured, be aware that password-reset links are written to the platform log. Anyone who can read that log — including a `docker compose logs` run by a colleague — can use a reset link to take over any account, including an admin account. Configure `EGMA_SMTP_URL` before granting log access to others.
</Warning>

<ParamField path="EGMA_SMTP_URL" type="string">
  An SMTP connection URL. Setting this turns on email delivery for invitations, signup verification, and password resets all at once.

  ```bash
  # Example
  EGMA_SMTP_URL=smtp://user:password@smtp.example.com:587
  ```
</ParamField>

<ParamField path="EGMA_MAIL_FROM" type="string">
  The display name and address used in the `From` header. Optional — defaults to a bare address when omitted.

  ```bash
  # Example
  EGMA_MAIL_FROM='Egma <egma@example.com>'
  ```
</ParamField>

## Model provider credentials

Persona versions choose the LLM, speech-to-text, text-to-speech, and voice.
Grader versions choose their judge model. The variables below supply only the
credentials needed to call those providers.

`egma self-host setup` does not ask for provider credentials. Put one current
key per provider in `.env`, then recreate the API and grader containers so they
receive the changed environment.

<ParamField path="EGMA_OPENAI_API_KEY" type="string">
  The deployment's OpenAI key. It can be used by simulation LLM, OpenAI STT or
  TTS selections, and by OpenAI-backed graders.
</ParamField>

<ParamField path="EGMA_DEEPGRAM_API_KEY" type="string">
  The deployment's Deepgram key for persona versions that select Deepgram STT.
</ParamField>

<ParamField path="EGMA_CARTESIA_API_KEY" type="string">
  The deployment's Cartesia key for persona versions that select Cartesia TTS.
</ParamField>

Egma Cloud can read the same three-key bundle from one AWS Secrets Manager
object instead of direct environment values. Set both selector variables or
neither:

<ParamField path="EGMA_PROVIDER_CREDENTIALS_SECRET_ID" type="string">
  The secret ID or ARN. The secret JSON uses `openai_api_key`,
  `deepgram_api_key`, and `cartesia_api_key`. The API and grader fetch its
  current value for each work item.
</ParamField>

<ParamField path="EGMA_PROVIDER_CREDENTIALS_REGION" type="string">
  The AWS region that contains `EGMA_PROVIDER_CREDENTIALS_SECRET_ID`.
</ParamField>

<Note>
  These credentials are not platform settings and are not stored in Postgres.
  A simulator receives only the keys required by its claimed work order.
</Note>

## Quick-start checklist

Run these commands to generate all nine required secrets at once, then paste the output into your `.env`:

```bash
echo "EGMA_ENCRYPTION_KEY=$(openssl rand -hex 32)"
echo "EGMA_AUTH_SECRET=$(openssl rand -base64 32)"
echo "EGMA_SIMULATOR_SERVICE_TOKEN=egma_st_$(openssl rand -hex 32)"
echo "EGMA_S3_INGEST_ACCESS_KEY_ID=$(openssl rand -hex 8)"
echo "EGMA_S3_INGEST_SECRET_ACCESS_KEY=$(openssl rand -base64 24)"

# Choose your own values for these — minimum 8 characters each:
echo "EGMA_S3_ACCESS_KEY_ID=<your-minio-admin-user>"
echo "EGMA_S3_SECRET_ACCESS_KEY=<your-minio-admin-password>"

# After first start, copy these from startup logs:
# EGMA_S3_READ_ACCESS_KEY_ID=<from-logs>
# EGMA_S3_READ_SECRET_ACCESS_KEY=<from-logs>
```

Then start the platform:

```bash
npx @egma/cli self-host up
```

`egma self-host up` sets `EGMA_BASE_URL`, `EGMA_LIVEKIT_API_KEY`, and `EGMA_LIVEKIT_API_SECRET` automatically.
