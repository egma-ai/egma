Platform settings contain one thing: the deployment's shared phone carrier
route. Model providers, model names, speech choices, voices, and grader choices
do not live here.

- Persona versions own the LLM, speech-to-text, text-to-speech, and voice used
  for simulations.
- Grader versions own the model used to judge a simulation.
- The deployment environment supplies provider credentials. See
  [Environment Variables](/configuration/environment-variables#model-provider-credentials).

The route lives in Postgres. Egma seals its SIP password with
`EGMA_ENCRYPTION_KEY`, so the route survives a restart and a database rebuild
from backup.

## Interactive setup

Run setup from the platform workspace as the instance owner:

```bash
npx @egma/cli login --url http://localhost:3101
npx @egma/cli self-host setup
```

Setup asks only for the carrier route. It never asks for provider keys, model
names, the Twilio Account SID, or the Twilio Auth Token. It also never creates
or changes anything in Twilio.

Use `--plan` to see the required input without writing anything:

```bash
npx @egma/cli self-host setup --plan
```

Use `--json` for an unattended run. Supply the route with the four
`EGMA_PHONE_*` variables listed below.

## Supported route shapes

Egma accepts two complete shapes:

| Authentication | Required values |
|---|---|
| Source IP | Trunk address and source number |
| SIP credential | Trunk address, source number, SIP username, and SIP password |

Egma refuses every partial shape. This stops one route from being mixed with
part of another route.

For Twilio, keep one account, trunk, source number, and credential list. Create
one SIP username and password for each developer and one for production. They
can all use the same trunk and source number.

## API setup

An organization owner can write a complete route through the API when the
instance serves one organization:

```bash
curl -sX PATCH http://localhost:3101/api/platform/settings \
  -H "Authorization: Bearer egma_sk_..." \
  -H "Content-Type: application/json" \
  -d '{
    "carrier_trunk_address": "trunk.example.com",
    "carrier_trunk_number": "+15551234567",
    "carrier_trunk_username": "egma-local",
    "carrier_trunk_password": "..."
  }'
```

The response never returns the SIP password. It returns only its last four
characters as a hint.

## Settings

| Setting key | Environment variable | Description |
|---|---|---|
| `carrier_trunk_address` | `EGMA_PHONE_TRUNK_ADDRESS` | SIP trunk hostname, with no scheme or path. |
| `carrier_trunk_number` | `EGMA_PHONE_SOURCE_NUMBER` | Source number in E.164 format. |
| `carrier_trunk_username` | `EGMA_PHONE_TRUNK_USERNAME` | Optional SIP username. Must be supplied with the password. |
| `carrier_trunk_password` | `EGMA_PHONE_TRUNK_PASSWORD` | Optional SIP password. Sealed at rest and supplied with the username. |

`EGMA_CARRIER_SETTINGS_SOURCE` decides how startup treats these environment
values:

- `platform` is the default. Startup seeds a missing route and then leaves a
  complete stored route alone.
- `environment` makes the environment authoritative. Each startup replaces the
  stored route with the complete environment route. Empty phone variables
  remove the stored route.

This choice does not depend on `EGMA_SINGLE_ORGANIZATION`.

<Warning>
  Back up `EGMA_ENCRYPTION_KEY` with Postgres. A database backup without this
  key cannot recover the stored SIP password or connection credentials.
</Warning>
