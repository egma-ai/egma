Egma onboarding runs inside the coding agent you already use. The coding agent
inspects the repository and asks when it needs the developer. Small CLI
commands perform the local and platform operations.

<Note>
  You need Node.js 22 or newer, a coding agent that can use Agent Skills and run
  shell commands, and a browser where you can approve sign-in.
</Note>

## 1. Install the CLI

Install the CLI once:

```bash
npm install --global egma-cli
```

The `write-egma-tests` skill is available for Markdown Test authoring:

```bash
npx --yes skills add egma-ai/egma \
  --skill write-egma-tests
```

<Note>
  The public `integrate-egma` skill is still being authored. Its Connection and
  monitoring guides are not complete. Follow this CLI workflow directly; do
  not treat installation of that skill as completed setup.
</Note>

Open the repository that contains your voice agent. Then give your coding agent
a complete goal, for example:

> Set up simulation testing and production monitoring for the Retell agent in
> this repository. Follow the Egma quickstart and use the promptless CLI.

The goal and platform come from your prompt and repository. The CLI does not
store them in a wizard or setup state machine.

## 2. Sign in and initialize the repository

The coding agent runs:

```bash
egma login
```

Egma prints a short code and approval URL, opens the browser when possible, and
waits. Approve the request in the browser. The CLI asks no terminal questions.

For a self-hosted instance, bind the exact URL:

```bash
egma login --url http://localhost:3101
```

Then initialize from the voice-agent repository:

```bash
egma init
```

`init` never creates a Project. It uses the Project attached to the login, or
selects the only available Project, then pulls its current Agents, Connections,
suites, and tests. If the login can access several Projects, the command lists
them and requires an explicit ID:

```bash
egma init --project prj_...
```

Running `init` again for the same Project refreshes the repository. If
`egma/config.yaml` points to another Project, move or delete the existing
`egma/` folder before you initialize again.

## 3. Let the coding agent find the target

The coding agent keeps repository discovery read-only. It finds the exact voice
agent, its platform, provider identity, prompt, tools, and production path from
committed source.

Choose one outcome in your prompt:

- **Testing** adds simulation access, authors Tests, and creates a Run.
- **Monitoring** configures production evidence without a simulation
  Connection, Suite, Test, or Run.
- **Both** completes both paths for the same Agent.

If several source targets are credible, the coding agent shows the evidence and
asks you to choose.

## 4. Register the Egma Agent

Check `egma/config.yaml` first. If the target is not listed, register only its
Egma identity:

```bash
egma agent register --platform retell --name Receptionist
```

For LiveKit, use `--platform livekit`. If `--name` is absent, Egma uses the
repository directory name.

`agent register` does not accept Access, Modality, provider fields, or
credentials. It prints the stable Egma Agent ID and refreshes
`egma/config.yaml`. Use that ID in later commands.

## 5. Add a Connection for testing

Skip this step for a monitoring-only request. A Connection is one way a
simulation reaches the Agent. Access, Modality, provider configuration, and any
setup credential all belong to `agent connection add`.

### Retell

First list Retell Agents, their attached phone numbers, and the current
Connection command shapes:

```bash
EGMA_RETELL_API_KEY=... \
  egma agent connection options --platform retell
```

The key is present only for setup. Egma never writes it to the repository.

Add a chat text-mode Connection:

```bash
EGMA_RETELL_API_KEY=... \
  egma agent connection add \
  --agent agt_... \
  --access retell-api-key \
  --modality chat \
  --retell-agent agent_...
```

Use `--modality voice` with `retell-api-key` for a Retell web call. A public
phone Connection uses the exact number returned by the options command:

```bash
egma agent connection add \
  --agent agt_... \
  --access retell-phone-number \
  --modality voice \
  --retell-phone-number +14155550111
```

The first Retell Connection binds the provider Agent and seals the provider
key. Later Connections reuse that stored identity and key.
If the phone Connection is first, include `EGMA_RETELL_API_KEY` and
`--retell-agent` exactly as in the first example.

To avoid an environment variable, a coding agent can start the CLI as a child
process and write exactly one JSON credential object, `{"apiKey":"..."}`, to
its standard input:

```bash
egma agent connection add \
  --agent agt_... \
  --access retell-api-key \
  --modality chat \
  --retell-agent agent_... \
  --credentials-stdin
```

### LiveKit

Read the current server-owned options first:

```bash
egma agent connection options --platform livekit
```

Project credentials are the normal choice. Add one voice Connection with:

```bash
EGMA_LIVEKIT_API_KEY=... \
EGMA_LIVEKIT_API_SECRET=... \
  egma agent connection add \
  --agent agt_... \
  --access livekit-project-credentials \
  --modality voice \
  --livekit-url wss://example.livekit.cloud \
  --livekit-agent-name receptionist
```

Use `--modality chat` to add a chat Connection. The coding agent may add both
when you did not limit the requested setup.

A customer token endpoint also supports voice and chat. It uses
`--livekit-agent-name` and `--livekit-token-endpoint`, with no `--livekit-url`,
because the endpoint returns the LiveKit server URL. Supply its auth headers
through `EGMA_LIVEKIT_TOKEN_ENDPOINT_HEADERS`.

If you specifically use a customer token endpoint:

```bash
EGMA_LIVEKIT_TOKEN_ENDPOINT_HEADERS='{"Authorization":"Bearer ..."}' \
  egma agent connection add \
  --agent agt_... \
  --access livekit-token-endpoint \
  --modality voice \
  --livekit-agent-name receptionist \
  --livekit-token-endpoint https://example.com/livekit/token
```

The CLI never writes provider secrets to an environment file. The coding agent
owns any runtime configuration needed by the LiveKit worker.

## 6. Author and push the first Suite

List the Project's valid personas:

```bash
egma persona list
```

Create one remote Suite and its local directory:

```bash
egma suite create receptionist-core --name "Receptionist core"
```

The coding agent writes the smallest grounded Test set under
`egma/tests/receptionist-core/`. It uses the `write-egma-tests` skill for the
Markdown format, personas, scenarios, expected behaviors, and test-level Mock
Tool answers. Each Test also carries its own `env`, including
`retell_dynamic_variables` for Retell or `job_dispatch_metadata` for LiveKit.
Every tool that a Test does not name runs for real.

Push the complete repository:

```bash
egma push
```

Push validates all local content before upload. There is no separate validation
command. If a remote version moved, pull, reconcile the files, and push again:

```bash
egma pull
```

## 7. Create the Run

Name the local Suite directory and the exact Agent and Connection IDs from
`egma/config.yaml`:

```bash
egma run create receptionist-core \
  --agent agt_... \
  --connection con_...
```

`run create` pushes the complete repository first. If push fails, it creates no
Run. On success, it prints the Run ID and a results URL based on the platform
origin in `egma/config.yaml`, then returns. Open that page to follow progress.

For a real phone Connection, the coding agent states the Suite, target, and
expected simulation count, warns that calls can cost money, and waits for your
approval before it runs the command.

Cancel one Run with its exact ID:

```bash
egma run cancel run_...
```

## 8. Set up monitoring when requested

Skip this section for a testing-only request.

For a Retell Agent that already has a Connection, reuse its stored binding and
credential:

```bash
egma agent monitoring setup \
  --agent agt_... \
  --platform retell
```

For a monitoring-only Retell Agent with no provider binding yet, add the
provider identity and one-time credential:

```bash
EGMA_RETELL_API_KEY=... \
  egma agent monitoring setup \
  --agent agt_... \
  --platform retell \
  --retell-agent agent_...
```

To stop future Retell pulls while keeping existing traces:

```bash
egma agent monitoring stop \
  --agent agt_... \
  --platform retell
```

For LiveKit, run the same Agent-scoped command with `--platform livekit`. The
CLI prints the public `integrate-egma` skill installation handoff and exits
incomplete. That skill's monitoring guide is still being authored. Follow the
[Python SDK](/integrations/python-sdk) or
[JavaScript SDK](/integrations/javascript-sdk) guide directly for now. The CLI
does not edit source, deploy runtime configuration, or claim that monitoring is
active.

## Keep tests in step

After onboarding, the normal loop is:

```bash
egma pull
# edit and review tests
egma push
egma run create <suite-directory> \
  --agent <Egma Agent ID> \
  --connection <Connection ID>
```

Delete remote resources through their local handles:

```bash
egma suite delete <suite-directory>
egma test delete <suite-directory>/<test-file.md>
```

Egma deletes remotely first and removes only the exact local target after the
platform confirms deletion.
