Egma onboarding runs inside the coding agent you already use. Public skills
tell it how to inspect a voice-agent repository and where developer approval is
required. Named CLI commands perform each operation without asking terminal
questions.

<Note>
  You need Node.js 22 or newer, a coding agent that can use Agent Skills and run
  shell commands, and a browser where you can approve sign-in. A global Egma
  install is optional.
</Note>

## 1. Install the public skills

Open the repository that contains your voice agent and run the bare CLI:

```bash
npx --yes @egma/cli
```

It prints the public skill install command and the exact coding-agent handoff.
It does not sign in, inspect the repository, start another process, or change
anything.

Install the three skills it prints:

```bash
npx --yes skills add egma-ai/egma \
  --skill integrate-egma \
  --skill write-egma-tests \
  --skill egma
```

Then give your coding agent this handoff:

> Use the integrate-egma skill to inspect this repository, integrate its voice
> agent with Egma, and run the first reviewed test suite.

Use `egma` in the examples below when it is installed. On a clean machine, the
coding agent can use `npx --yes @egma/cli` as the command prefix instead.

<Tip>
  For a self-hosted instance, run the bare command with its URL. The printed
  handoff tells the coding agent to use that platform.

  ```bash
  npx --yes @egma/cli --url http://localhost:3101
  ```
</Tip>

## 2. Approve sign-in in your browser

The coding agent's first operational command is:

```bash
egma login
```

For another instance it adds `--url`:

```bash
egma login --url http://localhost:3101
```

Egma prints a short code and an `approve_url`, opens the page when this machine
has a browser, and waits. You approve the code in the browser. The coding agent
does not approve it for you, and the CLI does not ask you to paste a secret into
the terminal.

```text
url: https://app.egma.ai
code: WDJBMJHT
approve_url: https://app.egma.ai/device?user_code=WDJBMJHT
browser: opened
waiting: for this code to be approved in a browser
status: stored
credentials: /home/you/.egma/credentials
```

If the browser cannot be opened, open the printed URL yourself. Continue only
after `status: stored` or `status: already-stored`.

## 3. Let the coding agent discover the target

The `integrate-egma` skill keeps discovery read-only. The coding agent traces
committed source to identify:

- the voice-agent platform and exact agent;
- the prompt and tool definitions;
- the provider identifier or publishing boundary;
- the entrypoint and registered dispatch name for LiveKit; and
- the production path used for monitoring.

If the repository contains several credible agents, the coding agent shows the
evidence and asks which one to integrate.

Choose one outcome:

- **Testing** creates a simulation connection, one reviewed suite, and one run.
- **Monitoring** enables production ingestion and reads its status. It creates
  no simulation connection, suite, tests, or run.
- **Both** completes the testing and monitoring outcomes for the same agent.

Before any remote write, the coding agent shows the exact Egma platform, agent,
provider target, modality, access method, and resources it plans to create or
reuse. Approve that setup only when every item is correct.

## 4. Connect the agent for testing

Skip this section for a monitoring-only integration.

### Retell

The coding agent sends the Retell key through standard input or the environment,
never through a command argument. It includes `--show-context` so the receipt
contains the non-secret prompt and tools that Retell runs:

```bash
EGMA_RETELL_API_KEY=key_live_... egma connect \
  --platform retell \
  --show-context \
  --retell-agent agent_... \
  --lanes text
```

The available lanes are `text`, `web-call`, and `phone`. Several comma-separated
lanes create several connections on one Egma agent. A phone lane may also need
`--phone-number <e164>`.

The `provider_prompt:` and `provider_tools:` lines are JSON facts for test
grounding. When `--repo-prompt <path>` is also used, the command reports whether
the committed prompt and provider prompt have drifted. It does not hide or
silently resolve that difference.

### LiveKit

The coding agent first reads the selected Egma instance's LiveKit catalog:

```bash
egma connect --platform livekit
```

This deliberately incomplete command is read-only. It prints the available
`modality_option`, `access_variant_option`, and `required_field` lines. The
coding agent shows any real choices to you before it runs the approved complete
command.

For the recommended project-credentials variant:

```bash
EGMA_LIVEKIT_API_KEY=... \
EGMA_LIVEKIT_API_SECRET=... \
egma connect \
  --platform livekit \
  --name front-desk \
  --modality voice \
  --access-variant livekit_room.project_credentials \
  --livekit-url wss://acme.livekit.cloud \
  --dispatch-name receptionist
```

The optional `--metadata <json>` value is passed as room and dispatch metadata
on this variant. For a customer token endpoint, the coding agent uses the
catalog's voice option, `--token-endpoint <https-url>`, and supplies the JSON
auth headers through `EGMA_LIVEKIT_TOKEN_HEADERS`.

LiveKit secrets are accepted only from these environment variables:

- `EGMA_LIVEKIT_API_KEY`
- `EGMA_LIVEKIT_API_SECRET`
- `EGMA_LIVEKIT_TOKEN_HEADERS`

The coding agent never prints or opens the secret source.

## 5. Create the first suite from valid personas

First list every persona available to the bound project:

```bash
egma personas
```

Each `persona:` line contains JSON with the persona's stable `id` and display
`name`. New tests use only those values. If the project already contains remote
suites, the coding agent runs `egma pull` before creating anything.

Create one approved suite:

```bash
egma suite create receptionist-core --name "Receptionist core"
```

The command creates the suite on Egma, then writes its stable ID and current
name to `egma/tests/receptionist-core/suite.yaml`.

The coding agent writes three or four distinct, grounded tests. It converts any
existing cases you supplied before it adds new coverage. Each Markdown test
names at least one persona and contains a scenario plus judgeable expected
behaviors.

For LiveKit testing, the coding agent also:

- connects the Egma SDK test entry to the selected worker;
- writes one grounded project-wide answer for each external-dependency tool in
  `egma/mock-tools.md`; and
- writes a test-specific mock answer only when one case needs a different
  branch.

Agent-runtime controls, such as completing or handing off a workflow, stay real.

## 6. Validate and review before publishing

The coding agent runs the repository's focused checks for any source changes,
then runs:

```bash
egma validate
```

`validate` is read-only. It parses the complete `egma/` folder and checks that
every persona reference resolves against the bound project's current personas.
It prints every local issue and writes nothing.

The coding agent fixes the named files until the command ends with:

```text
status: valid
```

It then reads every changed file back and shows you the exact source,
dependency, config, suite, test, and mock-tool changes. This is a new approval
boundary: setup approval did not approve the authored files.

After you approve publishing, the coding agent runs:

```bash
egma push
```

`push` uploads the complete repository as one atomic project change. If Egma
has a newer version, nothing is uploaded. The coding agent pulls, reconciles,
validates, shows the new diff, and asks for publish approval again.

## 7. Approve and run the suite

Before starting a run, the coding agent names the suite, agent, connection,
modality, and expected simulation count. You approve this run separately. For
a phone connection, the coding agent warns immediately before approval that the
command places real phone calls and can cost money.

For Retell or an already-running LiveKit deployment:

```bash
egma run receptionist-core \
  --agent "Front desk" \
  --connection text-1
```

When the repository has only one runnable target, the two selection flags can
be omitted. The command follows the complete run until execution and requested
grading are terminal.

For a local LiveKit worker, one command owns the worker and the run:

```bash
LIVEKIT_URL=wss://acme.livekit.cloud \
LIVEKIT_API_KEY=... \
LIVEKIT_API_SECRET=... \
egma run receptionist-core \
  --worker-entrypoint src/agent.py \
  --worker-dependency-manifest pyproject.toml \
  --worker-dispatch-name receptionist \
  --agent "Front desk" \
  --connection livekit_voice-1
```

All three worker flags are required together. The CLI checks the entrypoint,
manifest, installed worker environment, and LiveKit credentials before it
starts anything. It waits for the exact dispatch name to register, starts the
remote run, and always stops the local worker when the followed run completes,
fails, or is interrupted. `--no-follow` cannot be combined with these worker
flags.

## 8. Enable monitoring when requested

Skip this section for a testing-only integration. Monitoring has its own
approval because it changes production ingestion.

For Retell, the coding agent sends the key on standard input:

```bash
cat retell-key.txt | egma monitoring enable \
  --platform retell \
  --platform-agent agent_...

egma monitoring status
```

For LiveKit, the coding agent first adds `monitor_livekit(ctx)` to the selected
worker and runs its focused checks. After you approve the exact monitoring
target:

```bash
egma monitoring enable --platform livekit
egma monitoring status
```

The LiveKit command prints the two SDK environment lines and writes them to
`.env` only when Git already ignores that regular file. The coding agent does
not read the file or repeat its secrets.

A monitoring-only task is complete when monitoring is enabled and the status
receipt has been read. A both task is complete only when both the run and the
monitoring status have reached their required end state.

## Keep tests in step

After onboarding, the normal repository loop is:

```bash
egma pull
# edit and review tests
egma validate
egma push
# get run approval
egma run <suite-directory>
```
