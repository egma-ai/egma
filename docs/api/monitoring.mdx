Egma receives evidence of real production conversations in one of two ways.

**Egma pulls them.** An agent is bound to the platform that runs it, holds that
platform's API key, and has **Pull production calls** turned on. Egma then asks
that platform for the agent's finished conversations on a clock. This is the
only stored monitoring choice in the product, and it is made per agent rather
than per project.

**Your agent pushes them.** Your own process sends spans to Egma's OTLP door
using a project API key. Nothing is configured and nothing is selected: the
stored conversations are the whole record. See
[Egma Python SDK](/integrations/python-sdk) for the worker setup, and
[Traces](/api/traces) for the door itself.

Production conversations are read under **Monitoring** in the app, whichever
way they arrived.

All routes on this page use the normal Egma authentication rules. Pass the
project identifier in the `projectId` query parameter. A project-scoped API key
can omit it when the key already names the project.

## Discover Retell voice agents

**`POST /v1/monitoring/retell/discover`**

Checks one Retell API key and returns the voice agents it can see. Use it to
find the Retell agent identifier to bind an Egma agent to. This request does
not save the key.

<ParamField query="projectId" type="string">
  Project identifier. Required when the credential does not already select one project.
</ParamField>

<ParamField body="apiKey" type="string" required>
  Retell platform API key with Agent Read permission.
</ParamField>

<ResponseField name="agents" type="array">
  Voice-agent choices shaped as `{ id, name }`, sorted by name. Chat agents are not returned.
</ResponseField>

A key Retell rejects returns `422`. A key with Agent Read permission but no
access to conversation history will pass this check and fail later when Egma
tries to pull conversations, so give the key Retell **Monitor** or **History
Read** permission as well.

```bash
curl -X POST \
  "https://your-egma-host/v1/monitoring/retell/discover?projectId=prj_abc123" \
  -H "Authorization: Bearer egma_sk_..." \
  -H "Content-Type: application/json" \
  -d '{ "apiKey": "key_live_..." }'
```

## Retry one failed import

**`POST /v1/monitoring/retell/failures/{failureId}/replay`**

When Egma cannot import one production conversation after its allowed attempts,
it records an import failure and moves on rather than stopping on that
conversation. This retries the exact call the failure names.

It reads that call directly, so it still works after the call has fallen
outside the platform's normal 30-day list window. Egma claims each production
conversation once, so a successful retry cannot create a second copy of a
conversation that was already imported.

<ParamField path="failureId" type="string" required>
  Import-failure identifier.
</ParamField>

<ParamField query="projectId" type="string">
  Project identifier. Required when the credential does not already select one project.
</ParamField>

<ResponseField name="monitoringImportFailure" type="object">
  `{ id, status: "resolved" }` after a successful retry.
</ResponseField>

<ResponseField name="trace" type="object">
  `{ id, write }`, where `write` is `written` for a conversation this retry stored, or `already` for one Egma had already stored.
</ResponseField>

| Status | Meaning |
|---|---|
| `404` | No open import failure with this id in this project. |
| `409` | Another retry already owns this failure, or the platform still cannot supply a complete conversation. The failure stays open. |
| `422` | The platform rejected the agent's stored key. Update the key on the agent and try again. |
| `429` | The platform rate-limited the request, or this agent is already waiting before it asks again. The message says when to retry. |
| `503` | The platform did not answer. Try again. |

```bash
curl -X POST \
  "https://your-egma-host/v1/monitoring/retell/failures/mnf_abc123/replay?projectId=prj_abc123" \
  -H "Authorization: Bearer egma_sk_..."
```
