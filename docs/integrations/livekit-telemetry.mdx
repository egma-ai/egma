A LiveKit agent already emits OpenTelemetry. egma listens on the endpoint that telemetry is built to reach, so wiring the two together is configuration on the agent's side and nothing else — no SDK to install, no callback to register, no code egma asks you to write. This page walks the whole path: an agent talking to someone, and the exchange readable on screen in egma with its timings.

This is the telemetry path, for watching an agent that is already talking to real people. If you want to run controlled simulations against a LiveKit agent, the [LiveKit Testing](/integrations/livekit-testing) page covers that separately. Neither path requires the other.

The instructions below are written against LiveKit's Python agents framework, which is the one that exports OpenTelemetry today.

## Setup

<Steps>
  <Step title="Get a project-scoped API key">
    Sign in to egma. You land in an organization with a project already in it.

    Mint a key **against that project** — not against the organization. The terminal login flow is the shortest way:

    ```bash
    egma login
    ```

    The terminal shows a short code, you approve it in a browser and choose which project the key is for, and the key egma collects is scoped to that project by construction.

    You can also mint a key directly against the API using your browser session:

    ```bash
    curl -sX POST http://localhost:3101/api/keys \
      -H 'content-type: application/json' \
      -b "egma.session_token=$YOUR_SESSION_TOKEN" \
      -d '{"name":"livekit-agent","project_id":"prj_..."}'
    ```

    `GET /api/me` lists the projects you belong to and their IDs.

    <Warning>
      A key minted for the organization rather than a project files its telemetry under no project. The export is accepted, the spans are stored, and `GET /v1/traces` with that key returns them — but the dashboard shows nothing, because a signed-in browser reads the project its session is acting in. There is no error; the spans are simply not where the page looks. Mint the key against a project.
    </Warning>

    Keep the secret. It is shown once.
  </Step>

  <Step title="Install the LiveKit agents framework and OTLP exporter">
    LiveKit's own OpenTelemetry example lives at `examples/voice_agents/otel_trace.py` in the [`livekit/agents`](https://github.com/livekit/agents) repository. It is a small voice agent called Kelly with one tool that already builds a `TracerProvider` and calls `set_tracer_provider`, so its export destination comes entirely from environment variables — no code changes needed.

    Install what it runs on:

    ```bash
    pip install "livekit-agents[openai,silero,turn-detector]==1.6.7" \
                python-dotenv opentelemetry-exporter-otlp-proto-http
    ```

    If the example uses LiveKit Inference for its language, speech-to-text, and text-to-speech steps and you are running against a local development server rather than LiveKit Cloud, point those steps at a provider directly:

    ```diff
                 llm=FallbackLLMAdapter(
                     llm=[
    -                    inference.LLM("openai/gpt-4.1-mini"),
    -                    inference.LLM("google/gemini-2.5-flash"),
    +                    openai.LLM(model="gpt-4o-mini"),
                     ]
                 ),
                 stt=FallbackSTTAdapter(
                     stt=[
    -                    inference.STT("deepgram/nova-3"),
    -                    inference.STT("cartesia/ink-whisper"),
    +                    openai.STT(model="gpt-4o-mini-transcribe", use_realtime=True),
                     ]
                 ),
                 tts=FallbackTTSAdapter(
                     tts=[
    -                    inference.TTS("cartesia"),
    -                    inference.TTS("rime/arcana"),
    +                    openai.TTS(model="gpt-4o-mini-tts", voice="ash"),
                     ]
                 ),
    ```

    Add `from livekit.plugins import openai` to the imports. The `use_realtime=True` flag on the STT step is required — the fallback adapter only accepts a streaming recogniser.

    This is the only change to the agent itself. Everything in the next step is environment variables.
  </Step>

  <Step title="Configure your LiveKit server connection">
    You need a LiveKit server for the agent's room. Two options:

    <Tabs>
      <Tab title="Local development server">
        ```bash
        curl -sSL https://get.livekit.io | bash
        livekit-server --dev
        ```

        Development mode listens on `ws://127.0.0.1:7880` and accepts the well-known development key pair:

        ```bash
        export LIVEKIT_URL=ws://127.0.0.1:7880
        export LIVEKIT_API_KEY=devkey
        export LIVEKIT_API_SECRET=secret
        ```

        These credentials are public knowledge and exist only to make a first run easy. Never put them in front of anything you care about.
      </Tab>
      <Tab title="LiveKit Cloud">
        Use your project's values instead. `lk cloud auth` followed by `lk agent init` writes an `.env.local` holding all three. The URL is the `wss://` address shown on your project's settings page.

        If your agent is hosted on LiveKit Cloud and egma is running on your laptop, the agent cannot post telemetry to `localhost`. Either put a tunnel in front of your local egma, or run egma on a server with a reachable address and use that address in `OTEL_EXPORTER_OTLP_ENDPOINT`.
      </Tab>
    </Tabs>
  </Step>

  <Step title="Point the telemetry at egma">
    Set three environment variables. The agent code is unchanged:

    ```bash
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:3100
    export OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer%20egma_sk_..."
    export OTEL_SERVICE_NAME=livekit-voice-agent
    ```

    Three things about those variables — each one has cost somebody an evening:

    - **`%20` where the space goes.** OpenTelemetry defines this variable as a list of `key=value` pairs whose values are percent-encoded. A literal space is not a valid character there. Some SDKs pass an unencoded space through and the header arrives intact; others refuse the whole variable silently, and the symptom is an agent that exports nothing.
    - **The API port, not the web application port.** egma's pages and its API answer on one origin so a browser's cookie is valid for both — but telemetry carries no cookie. Point the exporter at the API port (`3100` in the default local setup).
    - **No `/v1/traces` on the end.** The exporter appends the signal's path itself. Give it the base URL only.

    Then start the agent:

    ```bash
    export OPENAI_API_KEY=...   # or whichever providers you use
    python agent.py start
    ```

    Use `start` rather than `dev` unless you are on LiveKit Cloud — development mode resolves end-of-turn detection to a hosted model.
  </Step>

  <Step title="Talk to the agent">
    With the worker running, join a room and speak. LiveKit's agents playground does this in a browser with a microphone.

    Alternatively, run the agent in `console` mode — no LiveKit server, no room, just your terminal microphone and speakers:

    ```bash
    python agent.py console
    ```

    `console` replaces `start`, so it skips the room entirely. The three `OTEL_` variables still apply — the telemetry leaves the same process the same way. Let the agent finish speaking before you start again, and let its job end when you are done: the batch processor exports every few seconds, and the example flushes what is left on shutdown.
  </Step>

  <Step title="Read the transcripts in egma">
    Sign in and open **Transcripts**. The exchange appears, newest first, with when it started, how long it ran, how many turns each speaker took, and the first thing the human said.

    Open a conversation to see the full transcript: alternating `human:` and `agent:` turns in order, each with how far into the exchange it happened and how long it took. Expand a turn to see the timed steps inside it — model calls, speech synthesis, tool invocations, turn detection, and speaking time.

    Transcripts arrive within seconds. There is no ingestion delay: what the exporter has sent is readable as soon as it lands.

    The same data is also available over HTTP using the same key:

    ```bash
    curl -H "authorization: Bearer egma_sk_..." \
      "http://localhost:3100/v1/traces?from=2026-08-03T00:00:00Z&to=2026-08-04T00:00:00Z"
    ```
  </Step>
</Steps>

## Anatomy of the steps under a turn

When you expand a turn in the dashboard, you see the individual steps that made it up. A few things to know before you go looking for something that is not there:

<Accordion title="There is no speech-to-text step">
  This version of the framework does not time recognition as a step of its own. The transcript, its confidence, and the recognition delay arrive as facts on the human's turn. `eou_detection` is the decision that the human stopped talking — not the transcription of what they said.
</Accordion>

<Accordion title="Model and speech steps nest several layers deep">
  Through the adapters that wrap them: `llm_node` → `llm_fallback_adapter` → `llm_request_run` → `llm_request`. Only the innermost one names the model that actually answered; the outer ones name the adapter. The nesting is kept as it arrived rather than flattened, so the time attributed to each layer is the layer's own contribution.
</Accordion>

<Accordion title="A turn with no words is normal">
  An agent turn that calls a tool, or that gets interrupted, has steps and timings and nothing to quote in the transcript. That is correct.
</Accordion>

<Accordion title="A step whose parent has not arrived yet appears at the top level">
  Steps are exported as they finish, and a parent finishes after its children. Reading the transcript while an exchange is still running can show a step outside the turn it belongs to. It moves under its turn once the turn itself is exported.
</Accordion>

<Accordion title="Unknown steps are stored, not discarded">
  Whatever egma's columns have no place for is kept verbatim on the row it arrived on. A step egma does not yet understand is stored rather than dropped.
</Accordion>

## Troubleshooting

| Symptom | Most likely cause | Fix |
|---|---|---|
| Dashboard is empty but `GET /v1/traces` returns rows | Key is scoped to the organization, not the project | Mint the key against the project (step 1) |
| Nothing arrives at all | Header encoding or wrong endpoint | Check `Bearer%20` (not `Bearer `), and that the endpoint is the API port with no path appended |
| `403` on export | Key belongs to a viewer role | Sending telemetry is a write — use a member's or admin's key |
| Sign-in is refused with an invalid origin | `localhost` and `127.0.0.1` are different origins | Use the origin that matches `EGMA_BASE_URL` on your instance |
| Worker never joins a room | Machine is under load | A LiveKit worker stops accepting work when the host is busy, and logs it. Wait for load to drop or use a larger machine |

## Try it without a LiveKit server

The egma repository ships a captured OTLP export from a real run of the example agent at `fixtures/livekit-otlp-trace/`. Replaying those files at `POST /v1/traces` fills the dashboard with a genuine transcript and needs no LiveKit server, no model credentials, and no microphone.

<Note>
  The fixture keeps the timestamps it was recorded with — the capture ran on 2 August 2026, from `18:04:40Z` to `18:05:53Z`. Replaying does not move them. Open the **Last 30 days** window (or set `from` and `to` explicitly) to see it — the default last-24-hours view will show nothing.
</Note>
