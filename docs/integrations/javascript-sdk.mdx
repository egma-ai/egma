The `@egma/livekit` package has two verbs, and the room decides which one acts:

- `await simulation(agent, ctx, session)` runs an Egma simulation. It reports
  the agent's tools, lets Egma answer the tools the running test mocks, and
  sends the agent's own spans to Egma as that simulation's record.
- `monitor(ctx)` sends production LiveKit spans to Egma Monitoring.

Calling one verb does not enable the other.

`simulation` is **required** for a LiveKit simulation. An agent that cannot
report to Egma throws `NotReported`, and the session does not start. See
[It is required, and it fails closed](#it-is-required-and-it-fails-closed).

## Install

```bash
npm install @egma/livekit
```

The package needs Node.js 22 or newer.

| Verb | Supported `@livekit/agents` versions |
|---|---|
| `simulation` | `>=1.5.5 <2` |
| `monitor` | `>=1.5.5 <2` |

Both verbs export spans, so the package requires `1.5.5`, the first LiveKit
Agents JS release with the public mock-tool hook and OpenTelemetry fan-out
bridge. Calling either on an older version gives a direct version error. You
do not need to pin to `1.6.4`.

The upper bound is LiveKit's next major release, not its next minor release.
Egma treats the public LiveKit v1 APIs as one compatible line. Its test matrix
pins the exact minimum, each available minor boundary, and the latest tested v1
release.

## Run a simulation

Create the agent and session, then call `simulation` once before `session.start`:

```typescript
import { simulation } from "@egma/livekit";
import { type JobContext, voice } from "@livekit/agents";

export async function entrypoint(ctx: JobContext) {
  const isEgmaChat =
    ctx.job.room?.name?.startsWith("egma-sim-chat-") ?? false;
  const agent = voice.Agent.create({
    instructions: "Help the caller.",
    tools: [checkCalendar, bookAppointment],
  });
  const session = new voice.AgentSession({ stt, llm, tts });

  await simulation(agent, ctx, session);
  await session.start({
    agent,
    room: ctx.room,
    ...(isEgmaChat
      ? {
          inputOptions: { audioEnabled: false },
          outputOptions: {
            audioEnabled: false,
            syncTranscription: false,
          },
        }
      : {}),
  });
}
```

The `egma-sim-chat-` branch keeps chat simulations on LiveKit's text path.
Keep independent audio publishers off in that branch too. Other room names use
the worker's normal voice settings.

It reads `EGMA_URL` and `EGMA_API_KEY`, the same two settings `monitor` reads,
or the matching `endpoint` and `apiKey` options.

In an `egma-sim-` room, `simulation`:

1. Installs the span export to Egma.
2. Connects the worker to the room if it is not connected.
3. Finds the one Egma participant.
4. Reports the agent's real tool names and schemas.
5. Asks Egma which tools this simulation answers for. Egma replies with exactly
   the tool names the running test writes under `## Mock tools`.
6. Installs LiveKit mock couriers for those names only.
7. Follows later agent handoffs in the same session.
8. Removes all mock state when the session closes or the job stops.

**Egma answers exactly the tools the running test names. Every other tool runs
its real implementation, and Egma is not in that path.** A test that names none
runs your agent against your real backend from end to end.

**Unmocked tools run real, and are recorded from the agent's point of view.**
The transcript of a simulation is the agent's own account of the conversation:
its turns, and every tool call it made, with the arguments the model sent and
the result it received. A call a mock tool answered is marked `mocked` on the
transcript, beside the tool's own name. A call Egma refused shows as the error the SDK threw
on that call.

A mock tool whose name never matches one of the agent's tools runs nothing and
leaves no trace: the courier waits under a name the model never calls, and the
record shows no call and no warning. Spell each tool exactly as your agent
registers it.

`simulation` has no total startup deadline. It waits while the simulation room
is active, so a slow token endpoint, cold worker, or late Egma participant does
not fail only because it crossed a fixed allowance. A token request and each
hello RPC attempt retain their own transport timeout. The SDK retries delayed method registration,
connection and response timeouts, and send failures with the same idempotent
tool report. A permanent refusal, room disconnect, or Egma participant
departure ends startup. The session does not start until Egma accepts the tool
list and the SDK installs every selected courier.

After your normal `session.start` returns, LiveKit publishes the worker's native
agent state, such as `listening`, `thinking`, or `speaking`. Egma waits for that
initialized state before it sends the first simulated input. This simulator-side
wait is governed by the simulation's configured duration. You do not add another
callback or readiness signal.

When that simulation ends, Egma finishes pending output and its exact participant
leaves the room. The SDK closes the `AgentSession` you supplied, which completes
LiveKit's native session trace, flushes the final evidence, and releases entrypoint
code that is waiting for session close. An abrupt room disconnect closes the
session as well. These listeners are installed only after the Egma participant
accepts the tool report in a simulation room.

The worker reads the running test's `job_dispatch_metadata` at
`ctx.job.metadata`, as one compact JSON string. With Project credentials, Egma
writes it directly to the dispatch. With a token endpoint, Egma sends it in
`room_config.agents[0].metadata`, and your endpoint copies that room
configuration into the token it mints. Egma adds no key of its own there and
leaves the room's metadata empty. See
[Agents and connections](/concepts/agents-and-connections).

### What it sends to Egma

The agent's own spans, over OTLP, to `EGMA_URL` with your project API key —
the same road `monitor` uses. Each span carries the room's name, so Egma files
the spans under the simulation that opened that room. They are batched at one
second and flushed when the session closes and again when the LiveKit job
stops, so the end of a conversation lands in Egma within a second or two of
the caller leaving.

That is the **agent's POV** of the simulation: its turns, its tool calls, its
own timings. Egma stores it beside what its own caller heard, and shows it on
the simulation.

### It is required, and it fails closed

Every way the exchange can end without a hello Egma answered throws
`NotReported`, so the session never starts and Egma ends that simulation with
the same finding from its own side. A simulation that ran without reaching Egma
would have called your real backends everywhere a mock tool was meant to answer,
and its record would say nothing about it.

The thrown message names the branch and then the two things to check, in the
order you can check them: the room and Egma's own side of it, then the
`@egma/livekit` package installed here. Egma's side ends that simulation with
this message:

```text
the agent did not report to Egma: no egma.hello arrived from the worker's
session, so this simulation isolated nothing and its record would say nothing
about the tools it ran. The Egma SDK is required for a LiveKit simulation —
check that the worker can reach the room and that Egma's participant was in it,
and check that `egma.simulation` is called on the agent's session before it
starts
```

| Situation | Result |
|---|---|
| Production room | Nothing changes |
| Simulation tool the test names | Egma answers |
| Simulation tool the test does not name | The real tool runs, and the call is on the transcript |
| Egma cannot be reached during a call | The call throws `ToolError`; the real tool does not run |
| Egma receives the call and refuses it | The tool throws `ToolError` |
| The room ends before Egma accepts the report | `simulation` throws `NotReported`; the session does not start |

### Production safety and process isolation

The first check reads only `ctx.job.room.name`. Every Egma simulation room
starts with `egma-sim-`. In any other room, `simulation` returns before it
connects, exports, sends a message, or changes a tool.

Two things are process-wide and neither can be made per-job. LiveKit stores
JavaScript mock tools in process-wide state, keyed by agent class. And the
exporter's resource carries the room this process files spans under, and is
fixed when the tracer provider is built. LiveKit Agents runs each normal job in
its own child process, so this costs nothing. A second overlapping session is
refused by the mock table; a second job in the same process is refused by the
exporter. Cleanup runs when the session closes or the job stops.

Egma joins the simulation room as `egma-persona` or
`egma-persona-<simulation id>`. The room name and participant forms are fixed,
published protocol values. Refuse the reserved `egma-sim-` prefix in any system
that mints your production room names.

## Monitor production LiveKit agents

Open **Agents → Connect an agent**, choose **Monitoring** or **Both**, and then
choose **LiveKit**. The guided flow shows the JavaScript package, hook, and
environment values that the worker needs.

For manual setup, create a project API key in **Settings → API keys**. Set the
API origin and key where the worker runs:

```bash
export EGMA_URL=https://api.egma.ai
export EGMA_API_KEY=egma_sk_...
```

For self-hosted Egma, use the published API address that the agent process can
reach, such as `http://localhost:3100` when the worker runs on the same host.

For a LiveKit Cloud deployment, put the values in a gitignored secrets file and
run:

```bash
lk agent update-secrets --secrets-file=.env.monitoring
```

Call `monitor` before `AgentSession.start`:

```typescript
import { monitor } from "@egma/livekit";
import { type JobContext, voice } from "@livekit/agents";

export async function entrypoint(ctx: JobContext) {
  monitor(ctx);

  const agent = voice.Agent.create({
    instructions: "Help the caller.",
    tools: [checkCalendar],
  });
  const session = new voice.AgentSession({ stt, llm, tts });
  await session.start({ agent, room: ctx.room });
}
```

You can pass configuration directly:

```typescript
monitor(ctx, {
  endpoint: "https://api.egma.ai",
  apiKey: projectKey,
});
```

If your process already has OpenTelemetry export, build that provider around
LiveKit's mutable fan-out and pass the same provider and registrar to Egma:

```typescript
import { telemetry } from "@livekit/agents";
import { NodeTracerProvider } from "@opentelemetry/sdk-trace-node";

const fanout = new telemetry.FanoutSpanProcessor();
const provider = new NodeTracerProvider({
  spanProcessors: [yourExistingProcessor, fanout],
});
provider.register();

monitor(ctx, {
  existingTelemetry: {
    provider,
    registerSpanProcessor: (processor) => fanout.add(processor),
  },
});
```

OpenTelemetry JS 2.x cannot add a processor to an already-built provider. The
registrar must add to the fan-out inside the exact provider you pass.

The helper adds an OTLP/HTTP protobuf batch exporter and flushes its last batch
when the job stops. It keeps LiveKit Cloud observability active. If another
integration installed a provider without a safe way to add a processor, setup
stops with a direct error instead of replacing it.

After deployment, the first production conversation appears under
**Monitoring** when the worker sends its spans. Egma cannot see a DNS, firewall,
or network failure inside the worker. If nothing appears, check the worker logs
and confirm it can reach `EGMA_URL`.

`monitor` also reads the room name first. It returns in an `egma-sim-` room, so
a simulation does not also appear as a production conversation. `simulation`
exports that conversation instead, filed under the simulation. Refuse the
reserved `egma-sim-` prefix when your own system creates production room names.
